# Diet — локальные фото и жизненный цикл файлов

Дата: 15 ноября 2026 года. **Статус: инженерный контракт TECH-005; файлов, Room-таблиц и Android-реализации ещё нет.** Продуктовые пределы — четыре фото на дату и 5 MiB на входной файл. Выбор, декодирование, качество и память определяет [обработка и память](photo-processing.md); здесь — владение, дисковый бюджет и согласование файлов с БД. Это оптимизированная копия для дневника, не архив оригинала.

## 1. Размещение и идентичность

Все личные постоянные файлы находятся в credential-encrypted области обычного application context. Относительные ключи хранятся в БД; фактический корень запрашивается у Context, абсолютный /data-путь не зашивается.

| Ресурс | Плановое размещение |
|---|---|
| Общий корень | `getNoBackupFilesDir()/diet/` |
| Единая Room-БД и sidecars | db/diet.db, WAL/SHM/journal рядом; фактические temp-пути также инвентаризируются |
| Visual DataStore | prefs/visual.preferences_pb, один экземпляр на файл |
| Неизменяемый master | `media/objects/<assetUUID>.jpg` |
| Текущий импорт | `staging/<batchUUID>/`, имена создаёт Diet, не provider |
| Служебные метаданные | metadata/ при необходимости; основной журнал операций и ссылки находятся в Room |
| Восстанавливаемые миниатюры | cacheDir/diet-media/, вне постоянных master |

MediaStore, DCIM, Downloads, shared/external и device-protected storage для личных данных не используются. NoBackup — постоянное приватное хранилище, не cache; пределы системного исключения описаны в [системное исключение](system-backup-policy.md). Фактические custom-пути Room/драйвера и DataStore надо проверить до первого APK с личными данными: нельзя молча вернуться к стандартным каталогам.

PhotoID — логическая фотография дня, AssetID — её неизменяемые байты. Одинаковый вход дважды создаёт разные PhotoID/AssetID; физической дедупликации в первой версии нет. Подпись, дата и связь с приёмом пищи принадлежат Photo, а не имени файла. Переименование/удаление оригинала в галерее после Ready не влияет на показ. Diet не изменяет исходник и не управляет его резервированием сторонней галереей.

URI используется только для foreground-импорта с временным grant. Persistable grant/долгое хранение URI не требуются: до завершения копирования редактор остаётся активным, при уходе импорт отменяется. При потере процесса pre-Ready batch не возобновляется из provider, нужен повторный выбор. Ни URI, ни исходное имя/путь, ни EXIF/GPS не становятся постоянной идентичностью фото или логом. Сеть облачного provider не равна сетевой функции Diet.

## 2. Владение и состояния

Логические сущности будущей Room schema v1:

| Сущность | Минимальные поля/связи |
|---|---|
| MediaAsset | AssetID, относительный objectKey, MIME JPEG, width/height, byteCount, SHA-256, mediaFormatVersion=1, профиль обработки/цвет/качество, lifecycle и integrity |
| MediaImportBatch / member | batchID, draftID, контекст даты, session generation, media-list revision, порядки членов, AssetID, фаза, собственные временные пути, резерв места, причина отказа |
| Photo / draft_media | PhotoID, AssetID FK, момент/дата, подпись/порядок; отдельные ссылки durable draft и факта |
| Pending command / lease | Владение ресурсом активной замороженной команды, импортом или чтением; истёкший процесс не сохраняет бессрочную lease |
| Cleanup entry | AssetID/принадлежащий задаче путь, фаза удаления, повторы/последняя ошибка; не только timestamp |

Готовность байтов и владение независимы. Ready не означает сохранённую запись: Asset может удерживаться draft, фактом и активным чтением одновременно. Законченный receipt с историческим PhotoID не является ссылкой, удерживающей файл навсегда.

Состояния: PREPARING → READY → DELETE_PENDING → DELETING → удалён. Отказ/отмена PREPARING → ABORTED/FAILED → очистка. Integrity MISSING/CORRUPT отдельно от владения: повреждение не стирает запись. Новая ссылка разрешена только на READY с подтверждённым файлом; DELETE_PENDING/DELETING нельзя воскресить простым FK insert.

## 3. Подготовка и граница атомарности

Room-транзакция не объединяется атомарно с произвольными файловыми операциями. Поэтому все постоянные байты подготавливаются **до** публикации новых draft-ссылок и до сохранения факта; после commit факта не требуется завершающее перемещение файла.

1. Короткая транзакция через общий writer выделяет batch/PhotoID/AssetID, сохраняет контекст редактора, generation и media-list revision, резервирует место. Транзакция не держится во время provider IO/decode.
2. Члены обрабатываются последовательно. Ограниченный поток копируется в source.part; после успешного чтения выполняются flush, fsync открытого дескриптора и close. Проверки и нормализация выполняются над этими собственными неизменными байтами.
3. Выход пишется в master.tmp через bounded stream: максимум 5 MiB записанных байтов, обнаруженный overflow прерывает попытку. Перед меньшим профилем прежний неполный master.tmp удаляется/обнуляется, попытки не копятся; IO-ошибка не маскируется под разрешённый size retry. Для успешного выхода encoder завершается, затем flush → fsync открытого дескриптора → close; проверяются JPEG, размеры/лимит, метаданные и SHA-256. Исходные байты нужны только до успешной подготовки текущего члена.
4. Под единственным media coordinator master переносится в свой уникальный objectKey на той же файловой системе. Назначение предварительно должно отсутствовать; совпавший существующий объект при recovery принимается лишь после проверки владельца/job/hash. Чужое/несовпадающее содержимое не перезаписывается.
5. Синхронизируются файл и затронутые каталоги. Неподдержанный/неуспешный durability-шаг не считается Ready; это надо проверить на выбранных устройствах. После проверенного master исходный source.part удаляется и место подтверждённо освобождается до следующего члена; при неуспешном удалении следующий raw не создаётся, batch прерывается. Все master пока принадлежат PREPARING batch.
6. Только если **весь выбранный batch** подготовлен и токен действителен, одна Room-транзакция повторно проверяет дату, generation, media-list revision и четыре слота, делает assets READY и добавляет весь набор draft_media с durable checkpoint. Ни одного нового фото при частичном отказе не добавляется.
7. Транзакция сливает только media-ссылки с последней версией того же draft, сохраняя более новые текст/подписи/поля. Независимая media-list revision отделяет ввод заметки от смены даты/фотонабора; новое фото не попадает в другой день. При конфликте набор не привязывается автоматически, пользователь повторяет выбор.
8. Явное «Сохранить» следует receipt-first из [контракт черновиков](drafts.md): найденный receipt возвращается ещё до изменяемых проверок. Для нового commandID одна Room-транзакция проверяет контекст/ревизии/лимит/READY, сохраняет Photo/момент/ссылки, receipt/result и закрывает draft. Неуспех остаётся draft, успешный факт не дублируется.

Между шагами 4–6 возможен постоянный файл без публичной ссылки; это известный объект PREPARING, доступный для recovery/очистки. Обратный порядок, когда факт объявлен сохранённым до готовности файла, запрещён. File/directory sync и rename не обещают абсолютной сохранности при любой неисправности носителя; источники: [Os.fsync](https://developer.android.com/reference/android/system/Os#fsync(java.io.FileDescriptor)), [Os.rename](https://developer.android.com/reference/android/system/Os#rename(java.lang.String,%20java.lang.String)).

## 4. Отмена, повторный вход и повреждения

| Событие | Ожидаемое поведение |
|---|---|
| Отмена picker / пустой выбор | Прежний draft и сохранённые фото неизменны |
| Ошибка любого члена до batch checkpoint | Ни один новый член не привязан; прежние поля/фото сохранены, собственные подготовленные ресурсы идут на очистку |
| Уход/отмена редактора во время IO/decode | Generation недействительна, поздний callback не пишет draft/факт; native slot/lease освобождается только после фактического завершения вызова |
| Process death до Ready-транзакции | Весь pre-Ready batch помечается прерванным после проверки журнала; старый durable draft восстановлен, новые файлы не добавляются автоматически; «Добавление фото прервано. Выберите их снова» |
| Process death после Ready checkpoint, до Save | Собственные masters и ссылки восстанавливают последний durable draft; это ещё не запись дня |
| Process death около Save | Сериализованный writer и receipt определяют исход, а не отсутствие callback; повтор не создаёт вторую запись |
| Отсутствует/повреждён master | PhotoID/подпись/дата остаются, показывается недоступность; нет молчаливого удаления, нулевого дня или подстановки декоративного фото |
| Отсутствует/испорчена миниатюра | Удалить производную и создать заново из master; ошибка cache не портит сохранённое фото |

При чтении проверяются принадлежащий приложению путь/тип, длина и допустимость декодирования; изменение объекта/подозрение на повреждение вызывает сверку SHA-256 вне UI-потока. На старте сверяется инвентарь метаданных/путей, не декодируется вся фотолента. Полная проверка хешей выполняется порциями в обслуживании, не блокирует первый экран. Hash — проверка целостности, не шифрование и не доказательство авторства.

## 5. Удаление и сборка мусора

Удаление фото/момента и отказ от draft снимают ссылки и создают cleanup-задание; это не делает весь каталог staging безопасным для удаления. Активные imports, draft refs, saved refs, frozen commands и живые чтения удерживают ресурс. Завершённые receipts не удерживают удалённые фотографии.

Общий media coordinator сериализует публикацию/удаление и получение read-lease. Перед открытием файла/декодированием reader атомарно проверяет READY и действующее владение, получает lease под тем же fencing; DELETE_PENDING/DELETING отвергает нового reader. Перед unlink короткая Room-транзакция заново проверяет отсутствие всех владельцев и leases, переводит объект в DELETE_PENDING/DELETING и тем самым запрещает новые ссылки. Затем unlink и sync каталога выполняются вне БД; завершающая транзакция фиксирует удаление. Ошибка unlink не считается освобождением места, повтор безопасен. Авария между фазами возобновляет tombstone; заранее освобождать место в счётчике нельзя.

Lease читающего native decode живёт до возврата native, даже после отмены UI. После запуска нового процесса старые process-scoped leases снимаются только когда прежний процесс точно отсутствует; durable команды/refs сохраняются. Общий один процесс/одна Room из [модель хранения](storage-model.md) остаются условием, не возникает второго независимого GC.

Сканер удаляет только объекты, принадлежность которым подтверждена журналом/AssetID, при отсутствии ссылок и после fencing. Возраст файла/название .tmp сами по себе не доказательство. Неизвестный/неподтверждённый объект помещается в приватную карантинную область metadata/ для диагностики без показа содержимого/логирования URI; не удаляется слепо. Нехватка места не разрешает удалять живую историю или masters.

## 6. Дисковый бюджет

| Область | Плановая граница |
|---|---|
| Один вход / один master | Каждый ≤ 5 MiB; входной счётчик останавливается на первом лишнем байте |
| Активная подготовка | Один batch ≤4, один raw в момент; до 25 MiB payload подготовки (не filesystem overhead): три готовящихся master + текущие raw и master, каждый по 5 MiB |
| Резерв | 32 MiB под новый batch, включая запас на метаданные/блоки; перед стартом после выделения резерва должно оставаться ≥128 MiB свободного места |
| Производный disk cache | LRU ≤128 MiB в cacheDir/diet-media/; временные производные входят в квоту, thumbnail необязателен |
| Постоянные masters | Без общего лимита лет/числа фото сверх четырёх на дату; автоматически по возрасту/давлению места не удаляются |

Резерв сериализуется с импортом, учитывает уже занятые собственные staging/незавершённые удаления и пересчитывается по фактическому свободному месту. Проверка свободного места предварительна: другие приложения/SQLite/WAL могут расходовать диск после неё. Каждый write/fsync/rename/БД commit обрабатывает ENOSPC/IO-ошибку. Cache можно очистить, live master — нельзя. При отказе остаются прежние данные и понятный выбор отменить/освободить место; история не обрезается.

После отказа собственные файлы очищаются по правилам §5; перед новым batch не копится бесконечная очередь неосвобождённых резервов. Если cleanup не смог завершиться и безопасного места нет, новый импорт блокируется, а чтение/исправление дневника сохраняется, насколько позволяют БД/система. Удаление приложения удаляет его приватные данные; восстановления не обещается.

## 7. Будущая проверка

Синтетические, не личные изображения/БД: death/IO fault после каждой фазы, failed sync/rename, один испорченный член batch, late callback, конфликт даты/photo revision, одновременный ввод текста, receipt replay, source gone, два одинаковых входа, missing/corrupt master, GC во время decode/Save, удаление и повторный вход, disk full, cache eviction. Проверять также путь master/DB/WAL/DataStore и отсутствие в backup/transfer по отдельному контракту.

Это планы приёмки, не выполненные испытания Android. Используемые лимиты памяти находятся в [контракте обработки](photo-processing.md); миграция mediaFormatVersion не равна миграции SQL и не переписывает действующие masters без отдельного плана из [миграции](migrations.md).
