# Diet — выбранный стек и организация приложения

Дата: 15 ноября 2026 года. **Выбранный пользователем Kotlin + Jetpack Compose + Room реализован после разрешения кода; minSdk29 сохранён.** JVM48/Lint0/debug/R8 unsigned проверены, API29 full80 и последующий UI24 PASS. Официальный API37.0 ps16k/x86_64 run17:81 PASS с test-only Espresso3.7.0; обычный API37/4 KiB run17 также прошёл81 тест за141,638с. Версии/SDK — в [baseline](android-build-baseline.md) и [каталоге](android-dependencies.md), результаты — в [validation](build-validation.md), функции — в [coverage](implementation-coverage.md). Физические/OEM-проверки и недостающие сведения TECH-001 остаются открытыми.

## 1. Принятый базовый стек

**Принято пользователем: нативное Android-приложение на Kotlin + Jetpack Compose + Room.** Это выбор для Android-only/offline объёма. Material3, Lifecycle/ViewModel, Coroutines/Flow, DataStore, Navigation3 и bundled SQLite выбраны инженерно; версии закреплены в каталоге. Подключённая библиотека не означает, что каждый её API уже используется: фактический UI-координатор сейчас `UiHost`, а не отдельный ViewModel/NavDisplay. Фото и собственная локальная копия реализуют принятый контракт с указанными в validation пределами испытаний.

| Часть | Текущая основа | Зачем Diet |
|---|---|---|
| Язык | Kotlin — принято | Один основной язык для Android UI, данных и проверяемых правил |
| Интерфейс | Jetpack Compose — принято; Material 3 с собственными цветами/компонентами макета — инженерный выбор | Темы, карточки, раскрываемые отчёты, анимации и доступность; Material не заменяет согласованный дизайн стандартным шаблоном |
| Состояние экранов | UiHost/Compose state, StateFlow, Coroutines; ViewModel/Lifecycle доступны в каталоге | Отдельные черновики/ошибки и постоянное восстановление контекста; LaunchedEffect/BackHandler связывают UI с координатором |
| История | Room 2 + BundledSQLiteDriver, версии по каталогу | Связанные записи, снимки, цели по датам, поиск, миграции и транзакции |
| Настройки | DataStore для независимых визуальных предпочтений | Тема/акцент/порядок блоков. Данные, которые должны изменяться одной транзакцией с фактами, остаются в Room |
| Вычисления | Отдельные Kotlin-правила без зависимости от UI/БД | Порции/рецепты, округление, N/Q/уровни, точные p/q; JVM/Room эталоны исполнены, полный каталог остаётся по coverage |
| Фото | Системный Photo Picker с document-fallback и постоянной копией в области приложения | Локальные фото и лента после перезапуска, без обязательного доступа ко всей галерее |
| Навигация/графики | UiHost со своим стеком и Compose BackHandler; Compose Canvas + текстовая таблица | Navigation3 подключён в каталоге, но NavDisplay не используется. Графики и выборки разделены, внешнего chart SDK нет |
| Напоминания | AlarmManager/setWindow и NotificationManager, Room outbox/occurrence | Нет exact-alarm разрешения; framework posting проверен, реальная Doze/OEM доставка ещё открыта |

Текущая организация — один Android app-модуль с пакетами UI/domain/data/media/notifications и отдельный JVM-only domain-checks для того же чистого ядра. Второе приложение не создаётся, DI связывается вручную. Новые зависимости вводятся только после проверки роли и совместимости.

### Границы хранения

DataStore не хранит дневник/снимки/планы. Профиль, факт, цель, полнота и история переносов записываются в согласованной Room-транзакции. Малое состояние экрана не заменяет постоянное хранение; bytes фото не помещаются в Bundle. Это реализует выбранные границы NFR-001/002/007, полнота испытаний которых описана отдельно.

Числовой контракт: [numeric-contract](numeric-contract.md). Логические сущности/атомарность: [storage-model](storage-model.md), постоянные [черновики](drafts.md) и [миграции](migrations.md). Room хранит связанные доменные данные и их drafts/receipts; независимые визуальные группы вместе со своими малыми drafts/tokens хранятся в одном DataStore. Общей распределённой транзакции между ними нет.

### Почему этот вариант

Текущая цель — одно Android-приложение с тесной связью с жизненным циклом, локальными данными, выбором фото и уведомлениями. Нативный стек прямо соответствует этому составу; это инженерная оценка по ТЗ. Flutter/React Native стоит пересматривать при отдельном решении о второй платформе. Оборачивание HTML-макета само по себе не выполняет Android-контракт хранения/миграций/фото/напоминаний.

## 2. Что проверено по первичным источникам

- Android рекомендует ViewModel, Coroutines/Flow и разделение UI/данных: [architecture recommendations](https://developer.android.com/topic/architecture/recommendations). Для Diet расчётный слой выделяется из-за правил истории и аналитики.
- Room предназначен для локальных структурированных данных: [руководство Room](https://developer.android.com/training/data-storage/room). DataStore подходит для небольших наборов настроек, а связанные/сложные данные требуют другого инструмента: [DataStore](https://developer.android.com/topic/libraries/architecture/datastore).
- Compose BOM согласует версии Compose-библиотек, но не является полной фиксацией всего Android/Kotlin/toolchain: [BOM](https://developer.android.com/develop/ui/compose/bom). Для Kotlin 2+ compiler plugin имеет собственную связь с версией Kotlin.
- Одновременно опубликованы ветки [Room 2.x](https://developer.android.com/jetpack/androidx/releases/room) и [Room 3.x](https://developer.android.com/jetpack/androidx/releases/room3). На дату чтения страницы показывают stable 2.8.5 и 3.0.3 соответственно. Room 3 использует другие координаты/пакет и KSP; нельзя смешивать примеры разных веток. Для Diet выбрана Room 2.8.5; причины и драйвер приведены в каталоге, Room 3 не смешивается с её координатами.
- Совместимые Android Studio/AGP/Gradle выбираются по [таблице AGP](https://developer.android.com/build/releases/about-agp) и [релизам Studio](https://developer.android.com/studio/releases), а не независимым выбором «последнего» каждого инструмента.

Версии закреплены в документах и version catalog; Wrapper/verification metadata и KSP/schema созданы. Прочитанные BOM/POM/девять AAR были первоначальным обоснованием, после которого граф и сборка проверены исполнением. Version catalog не называется lockfile; повторные проверки обязательны при изменениях.

## 3. История первоначальной проверки среды

До разрешения реализации первоначально проверялось только чтением, без установки:

- adb, sdkmanager и gradle не найдены в текущем PATH;
- стандартные каталоги Android Studio в Program Files и SDK в пользовательском AppData/Local/Android не найдены;
- команда java найдена в PATH, но версия JDK этим сеансом не подтверждена: запуск запроса версии не завершился и был прерван.

Это историческое наблюдение, не актуальный статус среды и не полный поиск установок. Затем в разрешённом этапе установлены изолированные CLI/JDK/SDK/Gradle, созданы проект/APK и запущены эмуляторы. Инструменты не обязаны находиться в глобальном PATH; фактические версии/проверки — в [build-validation](build-validation.md).
