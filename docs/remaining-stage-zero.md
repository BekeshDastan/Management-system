Дата: 15 ноября 2026 года. Статус: **инженерный выбор TECH-007/008 и общей части TECH-009 для разрешённой пользователем реализации**. Это документ, а не результат сборки, загрузки каталога или испытаний телефона. Предметные проверки ниже имеют статус planned / not run; неизвестная модель телефона близких и фактическая One UI остаются в [профиле](device-profile.md).

Аккаунт/синхронизация и расчётные рекомендации не добавляются скрыто; исключённая функция копирования/восстановления не возвращается. ## 1. TECH-007: мягкие локальные напоминания

### Платформенные факты и выбор Diet

Android поддерживает неточные alarms: `setWindow` не должен сработать раньше начала окна; при target 31+ окно меньше десяти минут обычно расширяется системой. Энергосбережение может отложить доставку за окно. Это факты [Alarm scheduling](https://developer.android.com/develop/background-work/services/alarms), а не обещание точности Diet. Стандартный `setWindow` откладывается в Doze до подходящего окна обслуживания; WorkManager также не даёт обхода Doze. [Doze / App Standby](https://developer.android.com/training/monitoring-device-state/doze-standby).

Выбран framework `AlarmManager.setWindow(RTC_WAKEUP, …, PendingIntent)` — API19, входит в min29. Окно Diet **15 минут от выбранного локального времени**. Применение — напомнить заполнить дневник, не медицинский сигнал или будильник. `setExact*`, `setAlarmClock`, `SCHEDULE_EXACT_ALARM`, `USE_EXACT_ALARM`, full-screen intent, постоянный foreground service и запрос исключения оптимизации батареи не нужны. Новая runtime-библиотека, GMS, сервер, сеть или WorkManager для этой функции не требуются.

В интерфейсе: «Около 08:00; Android может задержать напоминание при энергосбережении». 15 минут — запрашиваемое окно при обычных условиях, **не гарантированный максимум**. При выключенном телефоне, force stop, запрете уведомлений, OEM-ограничении либо до первого разблокирования после reboot доставка может отсутствовать. Ни сохранённый bool, ни успешный вызов API не доказывают, что пользователь увидел уведомление.

### Сохраняемый контракт и время

| Поле / поведение | Выбранное правило |
|---|---|
| Три вида | Питание, утренний вес, суммарный сон; отдельные время/дни и переключатель. Изначально выключены; исходные предложения времени/дней — в ТЗ |
| Источник истины | `reminder_specs` в Room: стабильный ID, вид, желаемое enabled, localTime HH:mm, выбранные дни недели ISO1–7, revision/generation; сохранение с outbox сверки ОС по контракту хранения |
| Разрешения / доступность | Не записывать permission как вечный bool. Отдельно вычислять фактический запрет приложения/канала, ожидание регистрации и ошибку планировщика; сохранённое желание пользователя при отказе не подменяет доступность |
| Режим времени | «По местному времени телефона»: текущий `ZoneId.systemDefault()` на каждой сверке; не закреплять исходный UTC offset и не прибавлять 24 часа к предыдущему instant |
| Следующее событие | Для каждого вида одна ближайшая разрешённая дата/время строго в будущем; не регистрировать repeating alarm и не ставить прошедший instant, который ОС могла бы немедленно доставить |
| DST | В несуществующее время сдвинуть local date-time вперёд на длину gap; при overlap выбрать первый из двух instant. Один вид — не более одного dispatch за соответствующую локальную дату, в том числе после возврата часов |
| Просрочка | При callback не ранее начала окна и не позже **2 часов** от рассчитанного instant, только в ту же локальную дату и при совпавших generation/зоне. Более позднее/устаревшее событие пропустить; переход суток/повторный запуск не порождают залп пропусков |
| Изменение настройки | Одна последовательная сверка cancel/replace на вид; callback старого generation игнорируется. Изменение времени после сегодняшнего dispatch не создаёт второй dispatch этого же вида за эту дату |
| Сбой регистрации | Желание и outbox остаются в Room; статус «Не удалось запланировать — повторить». Новое открытие/системный триггер повторяет сверку идемпотентно, без ложного «доставляется» |

Occurrence хранит ID вида, локальную дату, исходное localTime, вычисленные zone/instant и generation. Ключ дедупликации dispatch — `(reminderId, localDate)`, а не requestCode, текущие миллисекунды или `Intent` extras. Все ID/revision/date следуют общему контракту; личные показатели в payload не помещаются. При перемотке даты назад уже обработанная дата не получает новый dispatch; намеренное изменение настроек не очищает этот реестр. Настройки и системная операция не являются общей транзакцией.

Один coordinator последовательно сверяет outbox после save/enable/disable, возвращения в foreground, `BOOT_COMPLETED`, `MY_PACKAGE_REPLACED`, `TIME_SET`, `TIMEZONE_CHANGED` и каждого alarm callback. После callback сначала обеспечивает следующее будущее событие, затем пытается показать текущее. Если процесс прерван между Room и AlarmManager, следующий перечисленный триггер чинит расхождение; бессрочное фоновое самовосстановление без такого триггера не обещается. Для стабильного типа используется явный immutable `PendingIntent`; идентичность cancel/replace задаётся component/action/data/requestCode, а не только extras. [AlarmManager API](https://developer.android.com/reference/android/app/AlarmManager).

`BOOT_COMPLETED`, `TIME_SET` и `TIMEZONE_CHANGED` входят в исключения ограничений implicit broadcasts; подписываться только на нужные Diet события. [Broadcast exceptions](https://developer.android.com/develop/background-work/background-tasks/broadcasts/broadcast-exceptions). Нужен обычный `RECEIVE_BOOT_COMPLETED`; private alarm receiver не принимает произвольные внешние команды, системные actions проверяются явно. В приёмнике `goAsync` переносит короткую работу с диском с main thread, `finish()` обязателен; внутренний срок завершения — **8 секунд**, никакого импорта каталога/фото/долгой миграции внутри. [BroadcastReceiver](https://developer.android.com/reference/android/content/BroadcastReceiver#goAsync()). Если для удержания CPU при асинхронной обработке используется собственный partial wake lock, он ограничен **10 секундами**, освобождается в finally и требует только normal `WAKE_LOCK`; испытанием проверить отсутствие утечки, не запрашивать battery exemption.

Расписание остаётся в CE noBackup Room: не переносить личные настройки в device-protected storage. После reboot до первого unlock напоминания недоступны, после unlock `BOOT_COMPLETED`/foreground пересверяет будущие даты. [Direct Boot](https://developer.android.com/privacy-and-security/direct-boot). Force stop — пользовательский запрет фонового запуска, обходить его нельзя; Android15+ дополнительно отменяет PendingIntent, возобновление после действия пользователя требует пересверки. [Stopped state](https://developer.android.com/about/versions/15/behavior-changes-all#stopped-state).

### Уведомления, дедупликация и переход

На API33+ запросить `POST_NOTIFICATIONS` после явного действия «Включить», с коротким объяснением, не в первом запуске. Отказ/закрытие диалога/отзыв не блокируют дневник; системные настройки предлагаются по действию пользователя. На API29–32 runtime-диалога этого permission нет, однако системный запрет остаётся возможен. [Notification permission](https://developer.android.com/develop/ui/compose/notifications/notification-permission).

Три стабильных channel ID — питание/вес/сон; исходная важность DEFAULT без full-screen/агрессивного повторения, без попытки обхода пользовательского выбора новым channel ID. Проверять `areNotificationsEnabled()` и importance соответствующего канала; звук/«Не беспокоить» контролируются системой и не гарантируются. [Notification channels](https://developer.android.com/develop/ui/compose/notifications/channels). Текст нейтральный: «Можно заполнить питание», «Можно записать утренний вес», «Можно записать сон»; без цифр веса, рациона или оценок на экране блокировки. Предпросмотр текста не отмечается доставкой.

Room атомарно проверяет актуальность spec/generation/date и однократно закрепляет dispatch-claim. Системный app/channel permission проверяется непосредственно перед post; его изменение вне контроля Room и не является частью её транзакции. Повтор того же callback не вызывает второй `notify`; фиксированный notification tag/ID на вид обновляет его карточку, `onlyAlertOnce` предотвращает повторное оповещение уже существующей карточки. **Claim/OS-post не атомарны:** смерть между ними может пропустить одно уведомление. Claim не пересылается автоматически после неизвестного исхода; политика выбирает отсутствие дубля/залпа, а не ложную «exactly once» доставку. Следующие даты продолжают планироваться. Статусы claim/ошибка не называются «прочитано» или «гарантированно доставлено».

Нажатие — явный immutable Activity PendingIntent, без запуска Activity из receiver. Открывает соответствующую форму питания/веса/сна на актуальную дату телефона, показывает её пользователю и учитывает существующий черновик/подтверждение выхода; ничего не сохраняет автоматически. Если уведомление старое, его день не становится скрытым «сегодня». Удаление карточки не изменяет настройки и не создаёт факт. Автоматическое подавление по факту наличия записей или по рациону не вводится: это три простых напоминания из принятого объёма.

## 2. TECH-008: проверенный офлайн starter и изображения

### Выбранный источник и готовность

Источник общих исходных продуктов — **USDA FoodData Central, SR Legacy, финальный набор April2018**, доступный отдельно в CSV/JSON на [официальной странице downloads](https://fdc.nal.usda.gov/download-datasets/). Выбран фиксированный архив, а не постоянно меняющийся API/Branded или интернет-поиск. SR Legacy включает аналитические и расчётные значения; это усреднённые справочные данные, не анализ конкретной еды/бренда/рецепта. [Сравнение типов](https://fdc.nal.usda.gov/data-documentation/). Собственные продукты/рецепты и быстрый ввод работают независимо от starter.

FDC прямо публикует свои **данные** как public domain / CC0 1.0 и просит указывать источник. [Licensing в API Guide](https://fdc.nal.usda.gov/api-guide/#licensing). В приложении — локальная справка об источниках с USDA/FDC, типом/релизом и датой подготовки поднабора. Лицензия пищевых данных не является лицензией произвольных изображений. Runtime API, ключи, интернет-разрешение, удалённые картинки и скрытое обновление набора не нужны.

Инженерная цель наполненного релиза — **60 проверенных базовых позиций**: овощи/фрукты, крупы/бобовые, мясо/рыба/яйца, молочные, орехи/масла и прочие простые продукты. Это цель начального наполнения, не лимит пользовательского каталога и не подтверждение 60 готовых строк. Каждая строка отбирается по exact FDC ID, пищевой форме и четырём нутриентам; недостающие позиции не заменяются условными числами. Нельзя переносить макетные 51 позиции и названия национальных блюд с усреднённым вымышленным КБЖУ. Для плова/мантов/бешбармака пользователь составляет собственный рецепт из взвешенных ингредиентов и выхода; отдельная готовая строка допустима только с проверенным конкретным источником и описанием.

| Подготовка поднабора | Обязательное правило до поставки |
|---|---|
| Происхождение | Зафиксировать официальный URL архива, release, дату извлечения и SHA-256 фактически скачанных bytes; сохранить список FDC IDs и для каждой строки исходное английское описание/русское имя, состояние сырой/готовый, выбранные nutrient IDs/units/raw amounts и рецензию |
| База | Только **100 г съедобной части**, пока источник явно не задаёт другой проверенный вариант. `food_nutrient.amount` определён per100g, единица берётся из nutrient table. Не делать 100мл=100г, не подставлять порцию/плотность по виду продукта. [Field descriptions](https://fdc.nal.usda.gov/docs/Download_Field_Descriptions_Oct2020.pdf) |
| Четыре компонента | Выбрать по идентификаторам и сверить имя/единицу: Energy в kcal, Protein/Total lipid/Carbohydrate by difference в g; nutrient ID и старый nutrient number не путать. Ни позиции массивов, ни текстовое совпадение «Energy» без единицы не являются ключом |
| Пропуски и энергия | Все четыре значения должны присутствовать, быть числовыми и входить в numeric-contract. Явный источник 0 допустим; отсутствие, «<…», неизвестное значение не превращать в 0. Не выводить энергию заново по 4/9/4 и не подменять carbs net carbs |
| Точность / перевод | Читать исходные decimal как точные строки, без Float/Double и скрытого округления сверх выбранных шести знаков. Сырой/варёный, с кожей/без, жирность и съедобная часть сохраняются в русском названии/описании; два разных продукта не объединять одним переводом |
| Независимая сверка | Второе чтение выбранных source rows и пересчёта порции для **каждой** включённой строки; автоматические checks completeness/units/duplicates/decimal и ручная проверка соответствия имени. Ошибка строки блокирует её выпуск, не весь ручной дневник |
| ID / обновление | У каждой bundled позиции свой постоянный UUID и source ID отдельно; init идемпотентен. Удалённая пользователем позиция не воскресает при restart/update; обновление starter не переписывает правки пользователя/снимки истории. Изменённая пользователем строка помечается как изменённая, исходное provenance не выдаётся за проверку новых значений |

На этой документальной стадии прочитаны страницы источника, лицензия и структура полей; архив/конкретные строки/хэши **не проверены**. Web-инструмент не читает ZIP, read-only сетевое чтение из shell завершилось ошибкой DNS 11001; это не доказательство недоступности источника на другом этапе. До выполнения таблицы TECH-008 имеет выбранный источник, но **не готовый достоверный каталог**. Промежуточный APK может честно начать с собственных продуктов; наполненный релиз не объявлять завершённым без выбранного проверенного starter либо явно согласованного изменения наполнения.

### Изображения и оформление

Сохранить визуальный уровень v0.4: локальные food-иллюстрации/обложки, три акцента, шесть вариантов обложки, мягкие анимации, состояния успеха/пустоты и уменьшение движения. Уже имеющиеся 12 проектных фото-иллюстраций имеют запись генерации в [реестре assets](prototype/assets/README.md); это оформление, не фотографии съеденного, проверка состава или исходный nutrition dataset. Перенос в Android включает визуальную сверку, сжатие и реестр происхождения каждого файла/производного crop; новые внешние фотографии без установленного источника/права использования не добавлять.

Неподходящее изображение не приписывать конкретному продукту: использовать нейтральную иконку категории или явно декоративную обложку. Личные фото остаются только пользовательскими сохранёнными assetID по TECH-005; starter/обложки не попадают в фотоленту и не занимают лимит фото дня. Никакой лицензии на чужое фото не выводить из лицензии FDC или отсутствия водяного знака.

## 3. TECH-009: общие измеримые цели

Это выбранные **цели Diet**, не нормы Android, медицинские пределы или измеренные результаты. Опорное устройство — заявленный Samsung S23+ / 8ГБ; фактические ОС/One UI/ABI/refresh rate уточняются при измерении. Для неизвестного телефона близких цели пересматриваются по измеренному профилю отдельной записью, не молча; совместимость min29 от этого не исчезает. Эмуляторы E29–E37/N16 из [матрицы](android-test-matrix.md) проверяют поведение/ограниченные ресурсы, не доказывают скорость физического S23+.

| S1 | 365 дат, 10000 фактов еды, 1000 продуктов, 100 рецептов/100 шаблонов/500 планов, 200 фото; часть дат и нутриентов незаполнена, архивные приёмы и изменённые источники |

Наборы — проверочные объёмы, **не ограничения длительности истории, количества фактов или пожизненного числа фото**. Историю нельзя обрезать до 366 дат/всех записей в RAM. В S1/S2 воспроизводимый seed и source manifest задают количество сущностей/снимков, длины строк и разумные знаменатели; отдельный S3 проверяет complexity budget без превращения ошибки в 0/пропуск. Фото/числа не превышают собственные контракты ради нагрузочного теста.

### Пороги на опорном физическом устройстве

Для времени операций ниже `p95` — отсортированные wall-clock измерения, nearest-rank `ceil(0.95*n)`, не среднее; отдельные cold/warm/cache состояния. Не менее **30** повторов каждого применимого сценария после трёх отдельных прогревочных проходов; холодный старт без прогретого процесса измеряется отдельно. Ошибка/таймаут считаются провалом, не удаляются из выборки. Результаты включают median/p95/max и сырые обезличенные durations.

| Сценарий / границы измерения | Цель S0–S2 на S23+ |
|---|---|
| Cold launch | TTID ≤2000мс p95; TTFD ≤3000мс p95 до интерактивной главной с актуальным днём. Splash/пустой каркас без данных не считать fully drawn; первая установка/миграция измеряются отдельно |
| Warm / hot launch | До интерактивного экрана ≤1000 / ≤500мс p95 соответственно; state восстановлен без полного чтения истории/изображений |
| Обратная связь | Реакция кнопки/ввода/показ progress ≤100мс p95; success только после подтверждённого durable commit/checkpoint, не по анимации |
| Данные дня / календарь | Открытие другой даты/месяца с видимыми значениями ≤300мс p95; произвольная смена дат не запускает декодирование всех фото |
| Save одного факта/цели/веса/сна | Подтверждение durable операции и обновлённый UI ≤300мс p95; source/receipt/dirty-конфликт не обходятся ради скорости |
| Подтверждение 500 строк | Шаблон/план/копирование/рецепт ≤2000мс p95 без фото-декодирования; одна атомарная операция, повтор не дублирует |
| Поиск каталога / дневника / подписей | Debounce 150мс включён в ≤500мс p95 от последнего ввода до первых **50** актуальных результатов/точного пустого состояния; отмена устаревшего запроса, literal wildcards/Unicode по контракту, без потери фокуса |
| Отчёты / графики | Точные данные 365 дат ≤1000мс p95; S2 за все 3653 даты/100000 фактов ≤3000мс p95. Работа в фоне, старые результаты помечены или скрыты при смене периода; downsampling только рисования, не арифметики/доступного списка |
| Фото-лента | Первая metadata-страница ≤500мс p95; видимые thumbs из тёплого cache ≤500мс, холодного локального cache ≤2000мс p95. Master processing/provider latency измеряются отдельно по TECH-005, не маскируются этим порогом |
| Отмена тяжёлой операции | UI отзывается ≤100мс, вычислительная задача признаёт отмену на ближайшем bounded checkpoint ≤500мс в S2/S3; не освобождать native-slot до фактического возврата decoder по TECH-005 |
| Отрисовка | В 30-секундном прокручивании главной/каталога/ленты и раскрытии отчётов ≤5% missed-deadline frames на API31+, p95 frameOverrunMs ≤0; отдельный счёт startup/первого открытия. API29–30 — frameDurationCpuMs p95 ≤16.7мс при тесте60Hz, это не эквивалент полного GPU deadline |
| Память / утечки | На S23+: used Java heap обычной главной/отчёта ≤128MiB, фото-цикл peak ≤192MiB; total PSS фиксируется отдельно с целями ≤220/≤350MiB соответственно. После прогрева и 20 циклов день→отчёт→лента→фото→назад стабилизированный PSS не растёт более чем на20MiB; native/GPU не приравниваются к Java heap |
| Размер | ARM64 minified release APK ≤50MiB с иллюстрациями; debug/universal APK учитывается отдельно. Размер БД/WAL/всех личных masters измеряется, пользовательская история не удаляется ради порога APK |

Бюджет bitmap/decoder, один тяжёлый job и disk/cache пороги берутся **только из TECH-005**, формулу B здесь не дублировать. На low-memory E29 и при ограниченном heap проверяется соблюдение адаптивного B, reclaim/ошибки без потери данных/OOM; цифры S23+ не выдаются за универсальный heap cap. Память страницы результатов ограничена: metadata выдаётся страницами по50, UI держит не более трёх metadata-страниц плюс выбранные ID/контекст; bitmap cache и pinned изображения учитываются отдельно по processing. Пагинация не исключает поиск/отчёт по всей истории.

Длинные S3-вычисления либо завершаются точно, либо дают явную budget-ошибку; за **10 секунд** без завершения — управляемая отмена/ошибка без сохранения частичного результата, проверенная на выбранном scheduler. Синхронные SQLite/file I/O и полные расчёты не выполняются на main thread; deadline UI не заменяет арифметическую точность или Room-атомарность. Медленный диск/thermal throttle не скрываются из отчёта, условия записываются отдельно. При выключенных напоминаниях нет periodic polling, активных reminder alarms или удержанного wake lock; 8-часовой idle-прогон проверяет это, без обещания нулевого системного энергопотребления.

### Измерение, доступность и зависимости

Официальный Android различает [TTID/TTFD и cold/warm/hot](https://developer.android.com/topic/performance/issues/launch-time); [Macrobenchmark](https://developer.android.com/topic/performance/benchmarking/macrobenchmark-overview) требует измерять вариант, близкий к release, а не обычную debug-сборку. В протоколе фиксировать commit/APK SHA, minified/profileable variant, ART compilation mode/наличие Baseline Profile, fixture seed/counts, фактический телефон/API/RAM/heap/refresh rate, battery/thermal и свободное место. Не переносить результаты с эмулятора или профилирующей сборки на установленный пользовательский APK без уточнения.

Для будущей автоматизации выбран **test-only `androidx.benchmark:benchmark-macro-junit4:1.5.0` Stable**, подтверждён [release notes](https://developer.android.com/jetpack/androidx/releases/benchmark). Для benchmark-target при отсутствии подходящей транзитивной версии нужен `androidx.profileinstaller:profileinstaller:1.4.1` в benchmark-варианте — [официальный stable](https://developer.android.com/jetpack/androidx/releases/profileinstaller); приложение не получает сетевого/аналитического SDK. Подключение и полный Gradle-граф/AAR requirements проверить отдельно, точные новые зависимости вне этого файла не добавлены. JVM/Room/UI-тесты используют уже выбранный [каталог](android-dependencies.md).

`StartupTimingMetric` и `FrameTimingMetric` дают TTID/TTFD/CPU; frameOverrunMs доступен только API31+. [Metric definitions](https://developer.android.com/topic/performance/benchmarking/macrobenchmark-metrics). Startup p95 вычисляется из отдельных итераций, поскольку стандартная сводка сама не гарантирует нужный percentile. Trace/Perfetto и отдельные `dumpsys meminfo`/heap наблюдения используются без записи личного питания в имена trace/логи. Jetpack Compose не должен повторять дорогие вычисления в каждой composition. [Compose practices](https://developer.android.com/develop/ui/compose/performance/bestpractices).

Доступность — обязательный gate, не повод отключить анимации/оформление для всех: обе темы/три акцента, touch targets минимум48dp без перекрытия, TalkBack имена/порядок/состояния, текстовые значения графиков, системный fontScale1.0/1.3/2.0, крупный display size, IME/назад/поворот/resize и узкий профиль320dp. 320 браузерных px не Android dp. При reduced motion или нулевом системном масштабе анимаций — мгновенные/короткие переходы без бесконечной пульсации; success/ошибка остаются доступны текстом. [Compose accessibility defaults](https://developer.android.com/develop/ui/compose/accessibility/api-defaults).
