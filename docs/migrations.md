# Diet — версии хранения и миграции

Дата: 15 ноября 2026 года. **Статус: инженерный контракт TECH-004 для будущего приложения; миграции, схемы и APK ещё не созданы и не проверены исполнением.** Код приложения сейчас не разрешён. Основания продукта — [правила данных](data-rules.md), [ТЗ](product-spec.md) и [приёмка](acceptance-tests.md); выбранные Room 2 и BundledSQLiteDriver — в [каталоге зависимостей](android-dependencies.md).

## 1. Что версионируется

| Версия | Область и правило |
|---|---|
| Версия APK / versionCode | Выпуск приложения. Новый APK может сохранять прежнюю схему; номер выпуска не становится номером схемы |
| Room schemaVersion | Структура единой основной БД и её ограничений. **1 — номер первой будущей схемы**, не уже существующая база. Следующая структурная правка после её фиксации получает новую версию |
| draftFormatVersion | Формат полезной нагрузки [черновика](drafts.md); отличается от revision конкретного черновика и от схемы Room |
| Версия настроек | Формат/семантика независимых предпочтений DataStore, их малого preference_draft и receipt/token в одном файле. Не сбрасывается только из-за изменения Room; быстрые порции с ключом продукта и спецификации напоминаний остаются в Room |
| snapshotFormatVersion / calcContractVersion / textKeyVersion | Формат точного снимка и арифметики/Unicode-ключей по [numeric-contract](numeric-contract.md); не номер схемы. Прежняя история не пересчитывается по новым продуктам/целям |
| Версия локального медиа | mediaFormatVersion=1 для metadata/нормализованного JPEG по [хранению фото](media-storage.md); версия cache-производных отдельно. Изменение фото не требует автоматически переписывать все факты |
| Версия стартового контента | Происхождение/редакция проверенного каталога TECH-008; не заменяет исторические снимки и пользовательские продукты |

Имена логических сущностей, ID и транзакционные границы задаёт [модель хранения](storage-model.md); числовое представление — [numeric-contract](numeric-contract.md). Постоянные UUID остаются lowercase TEXT, revision — Long с проверяемым приращением; даты ISO сохраняются в согласованном диапазоне. Миграция переносит исходные десятичные/рациональные значения и календарные даты без пересчёта из нынешнего каталога, часового пояса или сегодняшних целей. Нельзя повысить schemaVersion вручную вместо фактического преобразования и проверки схемы.

До первого выпуска с личными данными нужно зафиксировать schema v1, экспорт её структуры и синтетическую фикстуру v1. Состояние HTML-прототипа не импортируется в Android автоматически: это не выпущенная версия схемы и не пользовательская резервная копия.

## 2. Экспорт схем и допустимый Git

В будущем проекте Room schema export обязателен. В Git сохраняются полученные компилятором описания схем всех выпущенных версий и определённые тестовые данные без личной информации. Экспорт включает структуру, индексы/ограничения и служебные сведения Room, а не записи дневника. Его фактическое содержимое проверяется перед коммитом.

В репозиторий не попадают реальные БД, WAL/SHM, дампы, фото, raw-черновики, профиль, пути личных файлов, ключи подписи или отчёты с личными значениями. Схемы и синтетические фикстуры не являются функцией экспорта/восстановления приложения. Такой функции по-прежнему нет.

Схема выпущенной версии неизменяема в истории. Исправление её миграции оформляется новым проверяемым выпуском и документированной цепочкой, а не подменой старого экспорта. До первого выпуска техническую v1 можно дорабатывать с пересозданием **только явно одноразовой синтетической тестовой базы**; этот приём не входит в обработку пользовательской БД и не заменяет тест миграции.

## 3. Какие изменения мигрировать автоматически

| Изменение | Решение Diet |
|---|---|
| Простое добавление nullable-поля, таблицы или индекса без изменения значения существующих данных | AutoMigration допустима после просмотра сгенерированного перехода и тех же проверок содержимого, что для ручной |
| Новое обязательное поле | Только с определённым смыслом для старых строк и доказанным заполнением; отсутствие/неизвестное не подменять 0. Без такого решения выпуск блокируется |
| Переименование/удаление поля либо таблицы | По умолчанию ручная миграция. AutoMigrationSpec возможна только для однозначного преобразования с отдельно проверенной сохранностью; удаление исторического содержимого не принимается как техническая уборка |
| Изменение единицы/точности, разбиение таблицы, новые FK/уникальность, перенос снимков/receipt/черновиков, изменение полноты или целей | Ручной переход с предметной фикстурой и проверкой каждого инварианта |
| Новый расчёт/новая версия продукта/цели | Не повод пересчитывать исторические снимки, полноту, даты или значения уже подтверждённого факта |
| Смена Room/SQLite driver, параметров журналирования, ABI | Не обязательно новая schemaVersion, но обязательны проверка открытия прежней БД, миграций и упаковки/native по матрице |

Автоматическая генерация не даёт права исправлять неопределённые данные. Конфликтующие значения/дубликаты не удаляются молча, не сливаются по имени и не округляются до нового типа. Для каждого такого набора заранее определяется сохраняющий смысл переход; если он ещё не определён, миграция не выпускается.

Для выбранного драйвера проектируется миграция на соединении SQLiteConnection. В текущем Room 2 соответствующий вызов уже находится внутри транзакции; старый путь только через SupportSQLiteDatabase не считать достаточным при setDriver. Конкретное использование API проверяется в разрешённом проекте, примеры Room 3 не копируются в Room 2. [Первичное API Room Migration](https://developer.android.com/reference/androidx/room/migration/Migration).

## 4. Поддерживаемые пути обновления

Для каждого будущего выпуска вести реестр: APK/versionCode, schemaVersion, версии форматов настроек/черновиков/медиа, поддержанные исходные версии, переходы и статус проверок. Сейчас реальных строк выпуска нет; вымышленные v2/v3 не объявляются существующими.

Правила реестра:

1. Из каждой реально выпущенной схемы, которая может остаться на устройстве, существует проверенный путь к текущей. Пользователь вправе пропустить промежуточные APK. До изменения этой поддержки требуется отдельное решение о сохранности данных; отсутствие пути не лечится удалением БД.
2. Проверяются соседние переходы и полный фактически выбираемый Room путь для каждой поддержанной исходной версии. Если введён прямой переход через несколько версий, он проверяется самостоятельно, а не по результату соседней цепочки.
3. Чистая установка текущей версии и миграция из старой создают эквивалентную целевую структуру. Значимые данные после миграции дополнительно сверяются с ожидаемым содержимым.
4. Выпущенные versionCode, schemaVersion и ID не переиспользуются с другим смыслом. Временные номера для экспериментов не становятся маршрутами пользовательского обновления.
5. Неподдержанная более старая либо более новая схема приводит к понятной ошибке открытия с сохранением файлов. Нет `fallbackToDestructiveMigration`, его вариантов для отдельных версий/downgrade, удаления файла или «создать пустой дневник» после ошибки.

Обновление APK проверяется поверх предыдущего подписанного APK с тем же package/signing identity, без uninstall и очистки данных. Это отдельная проверка от OS upgrade и будущего изменения target SDK: [Android-матрица](android-test-matrix.md). Подпись и способ распространения ещё не реализованы; ключи в Git не сохраняются.

## 5. Прерывание и ошибка миграции

До готовности целевой схемы запись пользовательских фактов и побочные действия приложения не начинаются. Пользователь видит состояние подготовки локальных данных; при ошибке — возможность повторить после устранения причины и понятное сообщение. Самопроизвольный сброс, очистка данных и повторный первый запуск не являются восстановлением.

| Ситуация | Обязательное поведение |
|---|---|
| Завершение процесса до commit транзакции миграции | При следующем открытии SQLite восстанавливает согласованное состояние; незавершённый переход не объявлен успешным. Путь повторяется только из фактической версии БД |
| Ошибка преобразования/валидации схемы | Не подтверждать новую версию, остановить открытие приложения для записи. Сохранить старые данные и диагностировать ошибку без вывода личных значений в лог |
| Нехватка места, SQLITE_FULL/IOERR | Объяснить невозможность завершить обновление, оставить файлы на месте; повторить после освобождения места/устранения ошибки. Заранее найденное свободное место не гарантирует успех: нужны место для журналов и временных страниц |
| БД обновилась, процесс завершился до обычного экрана | Следующий старт распознаёт целевую схему; миграция не применяется повторно, onboarding/начальные данные не сбрасываются |
| Повреждение БД/ошибка носителя | Не обещать, что SQL-транзакция исправит физическую порчу. Сохранить доступные файлы, прекратить небезопасные записи и описать ограничение; не выдавать пустую БД за прежнюю |
| Остался WAL/SHM после сбоя | Не удалять служебные файлы вручную. Открытие/восстановление выполняет выбранный SQLite; копирование одного основного файла не считается безопасным способом миграции |

Обязательство «сохранить старые данные» относится к логической неуспешной операции при работоспособном хранилище, а не гарантирует восстановление после любой аппаратной поломки. Планово выбраны WAL, включённые foreign keys и synchronous FULL; действительные значения и применение ко всем нужным соединениям проверяются чтением в будущем проекте. Если требуемый режим не установлен, продолжение записей не объявляется безопасным. Ускорять запись отключением защитной синхронизации нельзя. Readback настроек не доказывает работу аппаратного fsync при любой поломке. [Атомарность SQLite](https://www.sqlite.org/atomiccommit.html), [WAL и его файлы](https://www.sqlite.org/wal.html), [ошибки SQLite](https://www.sqlite.org/rescode.html).

Миграция БД не отправляет уведомления, не читает оригиналы фото из галереи и не удаляет/переименовывает файлы на стороне как часть SQL-перехода. Медиа и настройки имеют собственные версионированные переходы; общей SQL-атомарности для них не обещается. Для визуальных предпочтений их данные/draft/receipt изменяются в одном DataStore, без моста Room↔DataStore. Если после успешного перехода Room отдельный файловый шаг ещё не закончен, записанное состояние позволяет продолжить его без потери старых ресурсов и без ложного успеха всего обновления. Файловые шаги описаны в [media-storage](media-storage.md); миграция только ссылок не доказывает существование файла. CE noBackup-путь выбирается до первой v1. Если путь когда-либо меняется, смена factory не переносит старые DB/DataStore: нужен отдельный проверяемый переход с журналом, свободным местом и сохранением старого ресурса до подтверждения.

## 6. Старый APK, downgrade и rollback

- Штатная установка старого APK поверх нового может быть запрещена Android по versionCode; обходить это для обычного пользователя не требуется. Тестовые обходы не становятся поддержанным сценарием.
- Если старое приложение всё же получает более новую схему, оно отказывает в записи и сохраняет БД. Автоматический destructive downgrade запрещён. Обратные преобразования не объявляются поддержанными без отдельного полного контракта и проверок; сейчас они не выбраны.
- Rollback незавершённой транзакции возвращает согласованное прежнее состояние. Он не означает откат уже подтверждённой миграции к старой схеме и не обещает возможность безопасного запуска старого APK.
- После подтверждённой миграции исправление дефекта доставляется следующим совместимым APK с сохранением данных. Не предлагать uninstall/очистку/восстановление из несуществующей копии как штатный путь.
- Предыдущие синтетические APK/схемы и фикстуры сохраняются для будущих проверок, а не личные базы. Историю выпуска и результаты миграции нельзя заменить одним тестом текущей чистой установки.

## 7. Черновики, настройки и медиа при обновлении

Изменение payload черновика требует отдельного перехода draftFormatVersion. Перенос сохраняет raw-ввод, выбранную дату, ID и снимки; старый невалидный ввод не превращается в факт, 0 или текущие данные каталога. Неизвестный новый формат сохраняется без автоматического перезаписывания; пользователю объясняется невозможность продолжить именно этот черновик. Удалить его можно только явно. Подтверждённые записи не блокируются лишь из-за нечитабельного отдельного черновика, если целевая БД и остальные данные корректны.

Переход DataStore сохраняет выбранные предпочтения, их малые черновики и token/revision; повреждение/ошибка чтения не маскируется безусловной перезаписью дефолтами. Файл настроек не обрабатывается как Room-схема. Начальные значения разрешены для новой установки или явно отсутствующих новых ключей с определённым смыслом, а не для скрытой потери существующего выбора. Одна подтверждаемая операция visual-настроек и её draft/receipt остаются внутри одного DataStore, доменная операция — внутри Room.

Для медиа сохраняются стабильные photoID и связь с датой/приёмом. Пересоздание миниатюры не меняет исходник или личную подпись. Временные файлы очищаются только по подтверждённой принадлежности и отсутствию ссылок из факта/активного черновика/незавершённой операции; возраст файла сам по себе не доказывает, что он сирота. Политика — [черновики](drafts.md) и [файловый протокол](media-storage.md).

## 8. Ожидаемая проверка до выпуска

Это будущий набор, **не выполненные тесты**. Дополняет AN-003/004, ON-005 и CV-007/010; существующие приёмочные ID не переопределяются.

| Проверка | Ожидаемый результат |
|---|---|
| Каждая поддержанная старая версия → текущая; соседние и прямые пути | Целевая схема валидна, все синтетические значения/ID/связи сохранены |
| Пустая/непустая история, нулевой подтверждённый день, частичный день | Нет подмены полноты, пропуска или нуля |
| Смешанные единицы/точность, старые снимки удалённых источников, исторические цели | Нет пересчёта по нынешнему каталогу/цели, округления и сдвига календарных дат |
| Архив приёмов, шаблоны/планы и история переносов | ID и независимость данных прежние; один перенос не возникает вновь |
| Raw-невалидный draft, draft старого формата, receipt завершённой операции | Черновик не теряется и не применяется; завершённая операция не дублируется |
| Подготовленные/сохранённые фото, прерывание на каждом шаге | Нет удаления нужного файла, висячие ресурсы объяснимы/восстанавливаемы протоколом |
| Disk full / IOERR / kill до и после commit | Прежнее либо полное новое состояние; нет ложного успешного обновления/пустой базы |
| Нет пути / схема новее приложения / испорченное содержимое | Открытие для записи отклонено, данные не уничтожены |
| Чистая установка и APK update; API 29/37, native 16 КБ по применимости | Проверены структура, содержимое, реальный драйвер и пользовательский маршрут |

Приёмка схемы средствами Room дополняется собственными проверками строк/снимков/ограничений и повторного открытия. [Официальное руководство миграций](https://developer.android.com/training/data-storage/room/migrating-db-versions) описывает auto/manual, schema export и MigrationTestHelper, но само выполнение этих проверок в Diet ещё впереди. Для Room 2 используются совместимые с выбранной версией API, без переноса примеров Room 3.

Политика миграций определена документально. Конкретная schema v1, переходы, исполнительная проверка выбранных параметров хранения и доказательства AN-004 появятся после разрешения реализации; TECH-004 не закрывается одним этим документом.
