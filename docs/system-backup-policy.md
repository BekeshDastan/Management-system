# Diet — исключение системного копирования данных

Дата: 15 ноября 2026 года. **Статус TECH-006: реализация деклараций/CE noBackup и первые проверки выполнены; физическая/cloud/D2D/OEM-приёмка открыта.** Пользователь исключил резервные копии/восстановление. Здесь нет UI экспорта/импорта, пароля, облачного аккаунта или новой функции переноса.

Основания продукта — [D-003](decisions.md), [ТЗ](product-spec.md), [модель](storage-model.md), [черновики](drafts.md) и [миграции](migrations.md). База остаётся minSdk 29 / compileSdk 37 minor 0 / targetSdk 37 по [конфигурации](android-build-baseline.md).

## 1. Плановое решение и граница обещания

Diet запрещает передачу собственного состояния через управляемые приложением системные backup/restore-механизмы. Нужны одновременно: явный отказ в manifest, исключения обоих поколений правил, размещение личных файлов в CE noBackup и отдельная проверка каждого применимого транспорта. Отсутствие кнопки в приложении или одного флага недостаточно.

`allowBackup=false` задаётся явно. [Справочник application](https://developer.android.com/guide/topics/manifest/application-element#allowbackup) предупреждает об исключении: некоторые производители при target 31+ допускают D2D несмотря на этот флаг. Поэтому не обещается управление любым OEM; отказ облаку и отсутствие переноса проверяются отдельно.

План не требует GMS для дневника, не меняет выбранный минимум Android и не удаляет данные при обычном обновлении APK. Восстановление после process death/миграция собственной БД остаются обязательными; это не системное резервирование.

## 2. План размещения и полный инвентарь

Плановый общий корень — `getNoBackupFilesDir()/diet/` обычного credential-encrypted application context. Это постоянное хранилище, не cache. API получает фактический корень во время работы; абсолютные пути `/data/...` не зашиваются и не сохраняются как идентичность ресурса. [Context noBackup](https://developer.android.com/reference/android/content/Context#getNoBackupFilesDir()) исключает такие файлы из автоматического удалённого backup; это не универсальная защита от системного копирования.

| Состояние Diet | Плановое размещение / охват |
|---|---|
| Room: профиль/onboarding, каталог/рецепты, факт/полнота, цели/измерения | `db/diet.db` под общим корнем; все таблицы одной БД |
| Шаблоны/планы/история переносов, presets/reminder specs/outbox | Та же Room-БД, не отдельный разрешённый к переносу файл |
| Domain drafts, receipts/results, timeline/revision, media metadata | Та же Room-БД; raw, снимки, ID и fingerprint также личное состояние |
| WAL/SHM/rollback journal и временные файлы SQLite | Файлы рядом с custom DB и фактические временные пути включаются в runtime inventory; не исключать только имя основного `.db` |
| Visual DataStore: предпочтения, малые drafts, tokens/receipts/revision | `prefs/visual.preferences_pb` под общим корнем; включая поисковые запросы/фильтры/контекст возврата |
| Сохранённые изображения | `media/objects/<assetUUID>.jpg` под общим корнем; immutable JPEG master и фото-метаданные защищаются совместно |
| Подготовленные ресурсы и журнал файловых операций | `staging/<batchUUID>/` и `metadata/` под тем же корнем; ресурс активного draft не помещается в удаляемый системой cache |
| Восстанавливаемые миниатюры/кэш декодирования | Только `context.cacheDir/diet-media/`: derivatives/плейсхолдеры, не master/единственная копия и не источник правды |
| Служебные файлы библиотек, индексы, версии, диагностические артефакты | Инвентаризируются независимо от имени библиотеки; личное содержимое не выводится в логи/общие каталоги |
| Начальный контент/декоративные ресурсы APK | Поставляются в APK; не смешиваются с личными файлами и не считаются восстановленным дневником |

Пути согласованы с координатором: master находится в `noBackupFilesDir/diet/media/objects/`, подготовка — в `staging/<batchUUID>/`, derivatives — только в `cacheDir/diet-media/`. Изменение роли каталога требует обновить инвентарь, а не молча вынести фото из защищённой области. Личные файлы Diet не сохраняются в Downloads, MediaStore, shared/external storage или device-protected (DE) области. Будущая необходимость DE для напоминаний требует отдельного решения TECH-007 и проверки исключений; сейчас дублирования туда нет.

Для Room 2 требуется явно передать выбранное расположение и проверить фактический путь выбранного драйвера; имя БД само по себе не доказывает noBackup. DataStore создаётся с постоянным custom produceFile/путём и одним экземпляром на файл; стандартный files/datastore автоматически не считается noBackup. Factory не переносит ранее созданный файл в новый каталог: переход пути — отдельная проверенная миграция, не открытие пустого хранилища вместо старого. [Room API](https://developer.android.com/reference/androidx/room/Room), [PreferenceDataStoreFactory](https://developer.android.com/reference/kotlin/androidx/datastore/preferences/core/PreferenceDataStoreFactory). Неподдержанный custom path не заменяется молча дефолтом: исправление требуется до личных записей.

Runtime inventory проверяет отдельно корень app data (`root`), обычный filesDir (`file`), database/sharedpref и cache/code-cache, а не только выбранный noBackup-подкаталог. Непредусмотренный файл со значениями/изображениями Diet вне разрешённого расположения — дефект даже при запрещающих backup-правилах. WAL/SHM и фактические SQLite temp-файлы проверяются при записи/миграции; cache допускает только воспроизводимые производные.

## 3. Два поколения правил

| Runtime / target | Плановая декларация после разрешения реализации |
|---|---|
| Android 10–11 / API 29–30, APK target 37 | `allowBackup=false` и legacy-ресурс `fullBackupContent`: исключения всех доменов ниже |
| Android 12+ / API 31+, APK target 37 | `allowBackup=false` и ресурс `dataExtractionRules`: отдельные одинаково строгие исключения в cloud-backup и device-transfer |
| Будущий иной target/новый транспорт/новая библиотека | Повторная проверка правил и фактических путей; текущую таблицу не переносить как вечную гарантию |

[Изменения Android 12](https://developer.android.com/about/versions/12/behavior-changes-12#backup-restore) разделяют cloud/D2D и поколения правил. Legacy-ресурс нужен для поддерживаемых API 29–30; на API 31+ с новой декларацией он не заменяет device-transfer. Пустая или пропущенная секция не считается запретом. Шифрование cloud и условия requireFlags также не заменяют полное исключение состояния Diet.

## 4. Домены и относительные пути

Для каждого из всех девяти доменов таблицы планируется **exclude `path="."`** в legacy fullBackupContent, отдельно в cloud-backup и отдельно в device-transfer. Ни одного домена или поля нового формата не пропускать. Это таблица плана, не готовый XML.

| Domain | Область, относительно которой задан path |
|---|---|
| root | Корень приватных данных CE |
| file | filesDir CE |
| database | Стандартная область getDatabasePath CE |
| sharedpref | SharedPreferences CE; не любой DataStore по названию |
| external | Область getExternalFilesDir |
| device_root | Корень приватных данных DE |
| device_file | filesDir DE |
| device_database | Область БД DE |
| device_sharedpref | SharedPreferences DE |

`noBackup` и `cache` не являются именами domain. `.` обозначает весь соответствующий каталог, включая подкаталоги; это не маска `*`, не абсолютный путь и не `..`. Не полагаться только на root для других отдельно обходимых доменов. Эти имена и синтаксис проверены по [Auto Backup: domain/path](https://developer.android.com/identity/data/autobackup#XMLSyntax); cache/code-cache/noBackup штатно исключаются, но фактическое размещение файлов всё равно проверяется.

Текущая [справка о cross-platform transfer](https://developer.android.com/identity/data/autobackup#configure-cross-platform-transfers) описывает отдельную конфигурацию с сопоставлением приложения другой платформы. Diet её и custom BackupAgent не подключает, чужие bundle/team ID не придумывает. Отсутствие новой секции не объявляется доказательством запрета всех транспортов: личное состояние остаётся noBackup, новые/OEM-пути проверяются по применимости отдельно. Принятый продукт остаётся Android-only.

До первого APK с личными данными проверить итоговый merged manifest и скомпилированные ссылки ресурсов **обоих** форматов, все варианты сборки и добавленные библиотеками настройки. Не должно быть включённого backupAgent/key-value экспорта, разрешающих include-правил, утраченной секции или варианта с отличающейся политикой. Фактические XML/config созданы; содержимое после merge и ресурсной упаковки проверяется, а не предполагается по исходнику.

## 5. Что должно происходить с данными

| Событие | Ожидаемое поведение / предел вывода |
|---|---|
| Restart/reboot/process death | Подтверждённые данные и предусмотренные checkpoints прежние; noBackup не означает временное хранение |
| APK update поверх прежнего без uninstall | Данные сохраняются через миграции; новая политика не очищает собственную БД/файлы |
| Реальное обновление ОС | Проверка локальной сохранности отдельно от cloud/D2D; другой AVD не доказывает OTA |
| Новая чистая установка без переноса | Пустой дневник, незавершённый onboarding, NULL профильные числа/нет целей по модели; только штатные начальные приёмы/декор |
| Обычный uninstall с удалением app data → новая установка | Старых синтетических маркеров нет; сохранение данных/архивирование пакета не выдаётся за такой uninstall |
| Cloud restore / D2D на чистый приёмник | Личное состояние источника отсутствует, включая onboarding, drafts, prefs и медиа; передача только пустого APK допустима |
| Обнаружены старые системные снимки/результаты прежнего транспорта | Не обещать их удаление новым флагом/правилом; не удалять автоматически текущий дневник и не добавлять UI восстановления |

Стандартное app-specific хранилище удаляется при обычном uninstall; это не свойство обновления APK и не очистка внешнего оригинала выбранного фото. [Android app-specific files](https://developer.android.com/training/data-storage/app-specific). Глобальная галерея/её облако принадлежат пользователю и провайдеру; Diet не обещает управлять их копиями.

## 6. Будущая проверка AN-007 и ST

Фактический прогресс приведён в [build-validation](build-validation.md): API29 path inventory/compiled XML PASS и localtransport отказал backup. Остальные строки ниже остаются **planned / not run**, если явно не отмечены в отчёте; используются только синтетические данные. Нужны отдельные тестовые аккаунты/устройства/наборы; очистка, factory reset, транспорт и uninstall не запускаются на личном телефоне автоматически. Метод первой установки пользователем — APK-файл; это не разрешение USB/ADB или destructive-тестов сейчас.

Обязательные поля отчёта: APK SHA/commit, package/versionCode/signing identity без ключей; min/target/compile; фактические manifest/resource значения; модель/Android/API/оболочка источника и приёмника; тип/версия/активность транспорта и аккаунта; действительные CE/DE/custom пути; подготовленные маркеры, шаги и результат. Историю с реальными данными/учётные данные в Git не сохранять.

| Проверка | Достаточный ожидаемый результат |
|---|---|
| Статический inventory + реальные пути на API 29/31/37 | Все таблицы/журналы/drafts/prefs/медиа/кэши учтены; личного состояния вне выбранной области нет; обе ветви правил доступны нужной ОС |
| Действительный cloud transport, backup → чистое восстановление | Транспорт активен и попытка документирована; маркеры всех классов состояния не вернулись. Отключённый глобально backup/недоступная сеть сами по себе не PASS |
| Реальный Android D2D на согласованной паре | Проверены отдельные источник/приёмник и OEM-механизм; маркеров нет. Эмуляторный сценарий/локальный транспорт — вспомогательная проверка, не замена OEM |
| Дополнительный OEM migration path, если доступен | Собственный результат для этого механизма; успешный Google-транспорт не покрывает другой путь |
| Приёмник после переноса | Проверить не только первый экран: нет UUID/записей/фото/raw-drafts/token/поискового запроса источника; defaults не скрывают частичное восстановление |
| APK update, checkpoint/kill, миграция, существующий WAL | AN-001–004 и ST-001–003/008–011 сохраняют локальные данные; исключение backup не превращается в destructive fallback |
| Установочный режим/transport недоступен, модель близких неизвестна | Точное pending/blocked с причиной, не PASS по отсутствию восстановленных файлов |

[Официальное тестирование](https://developer.android.com/identity/data/testingbackup) различает транспорты и допускает диагностические симуляции. Полноценные cloud и D2D/OEM результаты записываются отдельно. Пустой результат `adb backup` не доказывает эти проверки; [Android 12 ограничивает ADB backup](https://developer.android.com/about/versions/12/behavior-changes-12#adb-backup-restrictions) отдельно от обычных транспортов.

## 7. Открытые условия выпуска

До первого APK с пользовательскими данными подтвердить actual noBackup/custom paths, декларации/исключения и применимые transport-проверки на выбранной матрице. Для близких пока известен Android 14, модель/OEM не названы; S23+/Android 17 сообщены пользователем, испытания ещё не выполнены. План связан с [Android-матрицей](android-test-matrix.md), [профилем](device-profile.md) и [TECH-006](technical-decisions.md).

Если OEM переносит исключённые данные, AN-007 получает дефект/ограничение, а не PASS с оговоркой; допустимость выпуска на этом окружении требует отдельного решения. Не обещается тотальный контроль OEM, rooted/скомпрометированной ОС, системных снимков экрана, ручных копий или ранее созданных облачных наборов. Пользовательский дневник не стирается ради имитации успешного запрета.

Документ определяет политику и будущие доказательства; TECH-006 не объявлен проверенным исполнением. Ни Android XML/config, ни приложение, ни transport-тесты этим документом не создаются.

## Исполнение первой версии

В build10 устранён действительно обнаруженный merged-manifest компонент: Room по умолчанию добавлял MultiInstanceInvalidationService с directBootAware=true. Приложение однопроцессное и не использует multi-instance invalidation; неиспользуемый сервис удалён manifest merger tools:node=remove. Privacy-тест не ослаблялся. На API29 compiled manifest после удаления проходит вместе с9исключениями в каждом legacy/cloud/D2D наборе; path inventory синтетической DB/WAL/SHM, DataStore/raw draft/tokens, master/staging/cache также PASS.

API29 LocalTransport: при временном включении только локального транспорта запрос bmgr backupnow app.diet ответил «Package app.diet with result: Backup is not allowed». Исходные disabled/transport настройки тестового AVD восстановлены. Это отказ конкретного транспорта, не успешный upload/restore и не испытание Google Cloud или Samsung Smart Switch. Продуктовая функция backups не создана; gate личных данных на непройденном физическом/OEM окружении остаётся открытым. Сборка/выдача тестового установочного APK не означает PASS этого gate.
