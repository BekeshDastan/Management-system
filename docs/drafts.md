# Diet — черновики, подтверждение и восстановление контекста

Дата: 15 ноября 2026 года. **Статус: инженерный контракт TECH-004 для будущего Android-приложения. Код, хранилища и проверки ещё не созданы.** Документ конкретизирует [сценарии](user-flows.md), [правила данных](data-rules.md) и ON-002/003/005, AN-001–003 из [приёмки](acceptance-tests.md), не добавляет аккаунт, синхронизацию или резервные копии.

## 1. Три разных состояния

| Состояние | Что означает |
|---|---|
| Ввод в памяти экрана | Последние клавиши/IME-композиция и живой предпросмотр. До подтверждённого checkpoint не объявляются надёжно сохранёнными |
| Постоянный черновик | Сохранённые raw-поля/контекст: доменный `drafts` в Room либо малый `preference_drafts` в DataStore. Могут быть неполными/невалидными; не попадают в дневник, уровни, поиск/фотоленту, отчёт или план как сохранённый состав |
| Подтверждённое состояние | Результат явного «Сохранить», «Добавить», «Применить» либо другого предусмотренного подтверждения после успешного commit. Наличие черновика или завершение поля не является таким подтверждением |

Сохранение **черновика** и подтверждение **данных** — разные операции. Автоматический checkpoint не нажимает за пользователя кнопку и не закрывает форму. Нельзя показывать «Запись сохранена», пока сохранён только draft. Продукт, отдельно сохранённый во вложенной форме, остаётся в каталоге при отмене внешнего добавления еды; отмена внешнего draft не откатывает уже подтверждённую самостоятельную операцию.

Источники версий библиотек — [каталог](android-dependencies.md), схемы/обновлений — [миграции](migrations.md). Физическая модель сущностей и числовое представление задаются соответствующими TECH-003/004; этот документ не создаёт вторую таблицу допустимых чисел. Backend формы выбирается заранее: одна подтверждаемая операция не требует одновременного изменения Room и DataStore.

## 2. Какие формы имеют постоянный черновик

В пределах одного редакторского контекста повторный вход продолжает существующий draft. Другой независимый редактор может иметь собственный ID; непреднамеренный повтор открытия не создаёт второй факт или скрыто не заменяет старый draft. Замена изменённого черновика другим требует предусмотренного подтверждения. Не добавляется отдельный пользовательский «менеджер черновиков» как новая функция.

| Форма / контекст | Что сохраняется отдельно от подтверждённых данных |
|---|---|
| Первый запуск | Шаг, необязательные имя/направление, raw-поля четырёх целей, явно выбранная/ещё не подтверждённая дата цели. «Настроить позже» завершает onboarding без применения частичной цели, сохраняя её для возврата |
| Профиль и редактор приёма | Raw-поля профиля либо имени приёма, ID/исходная revision. Подтверждённая перестановка/архивирование приёмов остаётся самостоятельной операцией; черновик не меняет историю |
| Цель / правка исторической цели | Четыре raw-поля, дата начала, ID/revision редактируемой цели, контекст затрагиваемого периода/подтверждений |
| Свой продукт | Имя/категория/база/имя единицы/четыре raw-КБЖУ, ID/revision при правке. Само открытие формы не создаёт продукт или еду |
| Рецепт | Имя, упорядоченные строки со снимками/количествами и raw-выход; промежуточно пустые/невалидные строки допустимы только в draft |
| Порция, быстрый ввод и исправление факта | Выбранная дата/приём, raw-количество или КБЖУ всей порции, исторический снимок либо явно выбранная замена источника, ID/revision записи. Кнопка быстрой порции меняет только draft |
| Копирование приёма / применение шаблона | Глубокие снимки выбранных строк, дата/активный приём назначения, шаг предпросмотра. До отдельного подтверждения строк в факте нет |
| Вес / сон | Выбранная календарная дата, raw-вес либо raw-часы/минуты, ID/revision записи, если она уже существует. Пустое поле не нормализуется в 0 |
| Личные моменты | Настроение/заметка, подписи/приёмы/порядок фото, существующие photoID и ссылки на подготовленные ресурсы. Выбор фото ещё не меняет сохранённый день |
| Создание/правка шаблона | Имя и собственные снимки/количества; отмена не меняет каталог/факт |
| План и перенос плана | Имя, плановая дата/приём, снимки строк; у переноса отдельно фактическое назначение и шаг предпросмотра. Факт, план и история переноса не сливаются |
| Настройка главной / оформление | Малый preference_draft в DataStore: полный набор редактируемых предпочтений и исходная revision; живой вид остаётся предпросмотром до сохранения |
| Быстрые порции | Доменный draft в Room: ID+база+единица продукта, исходная revision/подпись, raw-значения пяти слотов; сам продукт и еда от этого не меняются |
| Настройка напоминаний | Три набора включения/времени/дней и исходная revision. Системное разрешение и реальная доступность не сохраняются как выдуманное «Разрешено»; показ предпросмотра не отправляет уведомление |

Отчёт, график, каталог, календарь, поиск и фотолента хранят малый **контекст просмотра** в DataStore, а не черновик факта: выбранные даты/период/показатель, raw-запрос и фильтры, раскрытые разделы, ID выбранного элемента, позицию возврата. Результаты запроса и большие списки заново читаются из сохранённых данных. Невалидные даты фильтра остаются видимыми с ошибкой; запрос по ним не выполняется как будто введены другие даты.

Тема/шрифт/игровой переключатель или подтверждённый reset, которые в UX применяются сразу, сохраняются как самостоятельное действие. Не создавать для них лишний шаг «Сохранить» и не откатывать подтверждённый reset отменой ранее открытого редактора. Если reset заменяет текущий изменённый draft, подтверждение сброса объясняет это и закрывает/переинициализирует именно его.

## 3. Логический конверт черновика

Имена ниже — контракт полей, не Kotlin/SQL-схема. Постоянные ID — UUID в lowercase TEXT; revision — проверяемо возрастающий Long без переполнения. Даты — ISO `YYYY-MM-DD` в согласованных границах TECH-003; мгновение checkpoint не заменяет календарную дату записи. Числовые и текстовые пределы задаёт [единый numeric-контракт](numeric-contract.md). Raw-числовое поле допускает до 64 Unicode code points; предел Room-draft — 2 MiB UTF-8 без фото, каждого малого preference_draft — 8 KiB. При превышении явная ошибка без обрезки предыдущего checkpoint. Механизм подсчёта/сериализации проверяется до реализации.

| Поле / группа | Смысл |
|---|---|
| draftId, kind, draftFormatVersion | Стабильная идентичность редактора, вид формы и версия payload; не Room schemaVersion |
| draftRevision | Revision последнего надёжно записанного checkpoint. Внутренняя revision незаписанного UI отлична от подтверждённой |
| targetEntityId, baseRevision | Что редактируется и какая сохранённая версия открыта. Для нового объекта ID может быть заранее выделен, но объект ещё не существует как факт |
| selectedLocalDate, mealId | Явное назначение, в том числе прошлая дата и ID архивного приёма исходной истории; не индекс текущего списка |
| rawFields | Точные строки ввода, включая `""`, `"1,"`, невалидный текст и незавершённое число. Не только успешно распарсенное последнее значение |
| payload: шаг/строки/sourceSnapshots | Шаг, порядок/ID временных строк, исходные снимки с базой/единицей/точными КБЖУ и введённые количества. Снимок порции рецепта компактный: четыре точных p/q; полное дерево редактируемых ингредиентов внутрь строки не копируется. Снимки не перечитываются автоматически из изменившегося каталога |
| payload: returnContext | Маршрут/ID происхождения, период/фильтры/разделы и сведения для понятного возврата. Не копия всего результата поиска |
| draft_media | Связи draftId → mediaAssetId с ролью existing/staged и порядком; без байтов/bitmap в payload или Bundle |
| operationId, payloadFingerprint | Замороженное подтверждение и его идентичность. Изменение подтверждаемого payload означает новый operationId; raw-input fingerprint не является обезличиванием и не выводится в общие логи |

Ошибки валидации и вычисляемый предпросмотр восстанавливаются из raw-полей/снимков по текущему совместимому контракту; не сохраняются как альтернативная истина. Если новый формат/правило не понимает старый draft, он не обнуляется: [политика обновления](migrations.md).

Изменённый продукт/удалённый источник не заменяет снимок в уже открытом рецепте, плане, шаблоне или порции. Источник может стать недоступным для повторного выбора, но сохранённая копия остаётся. Для «обновить из источника»/«заменить источник» нужен явный шаг и новый предпросмотр. Исчезнувший targetEntityId не превращает редактор старой записи в создание новой без отдельного выбора пользователя.

## 4. Checkpoint и предел гарантии восстановления

Надёжный checkpoint означает завершённую запись draftRevision и payload в локальное хранилище. UI может отзывчиво показывать незаписанный ввод, но не объявлять его принятым checkpoint. В фоне/при kill нет гарантированного времени на последнюю запись; onStop/onSaveInstanceState не становятся единственным способом сохранения.

Обязательные точки checkpoint:

1. Завершение редактирования поля — окончание IME-композиции и blur/Done. Сохраняется в том числе невалидная строка; полная валидация формы не нужна для сохранения draft.
2. Переход к следующему/предыдущему шагу, выбор даты/приёма/источника, добавление/удаление/перестановка строки или подготовленного фото. Структурный переход признаётся завершённым после успешного checkpoint.
3. Открытие предпросмотра подтверждаемой операции, согласованный переход во вложенный редактор и «Настроить позже». Сначала сохраняется нужный контекст; сбой не маскируется успешным уходом.
4. Явное подтверждение сохранения сначала фиксирует соответствующий payload/operationId; далее действует протокол commit. Выход с отказом от изменений, наоборот, выполняет отдельный discard.

Между точками разрешён debounce для уменьшения потерь последнего ввода; его задержка выбирается по TECH-009. Он не гарантирует сохранение каждого клавишного события. После уничтожения процесса возвращается последний **успешно подтверждённый checkpoint**; более свежий незаписанный ввод может отсутствовать. ON-002 проверяется после завершённого checkpoint поля, AN-002 — в воспроизводимой точке, отдельно от теста прерывания незаконченной записи.

При ошибке checkpoint остаются текущий экран/raw-ввод и последняя сохранённая версия; показывается, что продолжение не сохранено, доступен повтор. Переход, который обещает сохранённый шаг, не завершается ложным успехом. После внезапного уничтожения процесса гарантируется лишь предыдущий checkpoint. Переполнение диска не делает невозможную запись сохранённой.

Очередь записи на один draft сериализована. Поздний ответ старого запроса не перезаписывает новый checkpoint, завершённый/discarded draft не оживает из отложенного debounce. Закрытие/удаление и запись используют revision/состояние и проверяются на гонку. Повторное открытие той же формы связывается с тем же draftId, пока он не завершён или явно отброшен.

## 5. Назад, отмена, прерывание

| Действие | Поведение |
|---|---|
| Назад/отмена/уход к другой записи из изменённой формы | Подтверждение отказа от несохранённых **данных**. «Продолжить редактирование» оставляет форму/draft; подтверждённый отказ удаляет/закрывает draft и возвращает исходное сохранённое состояние |
| Выход из неизменённой формы | Возврат без лишнего диалога; пустой технический draft можно закрыть, не создавая факт |
| Blur/переход шага/вложенный редактор | Checkpoint, без discard и без commit факта. Диалог о потере данных не появляется на каждый blur |
| Home/фон/поворот/пересоздание процесса/reboot | Не считать намеренным discard. После восстановления предложен/открыт предусмотренный контекст и последний checkpoint; явного сохранения за пользователя нет |
| Отмена live-предпросмотра оформления | Вернуть подтверждённые предпочтения, закрыть именно этот draft; фото/история/цели не меняются |
| Отмена системного picker | Сохранённый день и остальная форма прежние; случайно подготовленный ресурс не становится фото факта |
| «Настроить позже» в onboarding | Завершение onboarding без активной частичной цели; goal-draft остаётся доступным для последующего продолжения |

Подтверждение удаления факта и подтверждение discard — разные действия. Если пользователь отменил удаление, исходная запись остаётся; если подтвердил discard редактора, исходная запись также остаётся. При неуспешной записи discard нельзя сообщать, что draft исчез навсегда: повторный вход сверяет фактическое состояние, а задержанный checkpoint не должен воскресить его после успешного закрытия.

Открытие уведомления, другой даты или результата поиска не перезаписывает текущий dirty draft. Сначала разрешается намерение ухода/замены; затем новый контекст. Возврат из редактора сохраняет query/фильтры/период/раскрытие происхождения без включения черновика в результаты.

## 6. Явное сохранение в Room и защита повтора

**Recovery/retry известной команды сначала читает receipt по operationId/fingerprint.** Готовый совпадающий результат возвращается до checkpoint и всех изменяемых предусловий: сегодняшней даты, активности приёма, наличия исходного каталога/медиа и revision. Живой/открытый draft для lookup не нужен. Receipt хранит originDraftId/confirmedDraftRevision и результат; после закрытия/очистки raw-draft связь результата остаётся. Удалённый впоследствии факт показывается как недоступный результат прежней операции, а не создаётся заново.

Для ещё не выполненной команды:

1. Зафиксировать текущий checkpoint и заморозить payload, operationId/fingerprint, назначение и ожидаемые revision. Прямые действия без формы также получают сохраняемый идентификатор команды. UI блокирует повтор на время работы, но это не единственная защита.
2. В одной Room-транзакции **повторно сначала** проверить receipt. Если он уже существует — вернуть совпадающий результат; при ином fingerprint — конфликт. Только если receipt отсутствует, проверить raw-поля по TECH-003, даты/активность назначения, готовность подготовленных ресурсов, baseRevision и goalTimelineRevision. Изменение цепочки целей требует нового предпросмотра/подтверждения.
3. Записать все связанные данные/полноту/историю переноса, новые revision и receipt с originDraftId/результатом, завершить именно подтверждённую версию draft. Проверки и изменения не разделяются чтением вне транзакции. Полночь/смена зоны не переносит selectedLocalDate; неподтверждённая дата цели первого запуска уточняется явно.
4. После успешного commit показать результат. Если процесс завершился до показа успеха, следующий вход идёт через receipt-first и не повторяет команду.
5. Если после завершения предшествующего выполнения и согласованной проверки на очереди записи receipt отсутствует, эффект не подтверждён; прежние факты и последний checkpoint остаются. Одно чтение отсутствующего receipt, пока прежняя команда ещё выполняется, не доказывает rollback: исход остаётся неопределённым, retry с тем же ID снова сериализуется через writer. Повтор требует действия пользователя с тем же замороженным намерением; создание новых фактов при старте автоматически не выполняется.

operation_receipts.operationId уникален. Тот же ID и fingerprint возвращает прежние ID результата; тот же ID с другим содержимым — конфликт. После изменения команды нужен новый ID. Намеренное повторное применение шаблона/плана/копии — отдельное подтверждение и новый ID; история переносов плана предупреждает о повторе.

При сбое не появляются отдельно строка, изменённая полнота, половина состава или закрытый без результата draft. Если свежий checkpoint не записан, нельзя обещать его восстановление после kill. Отмена coroutine/потеря ответа не доказывает rollback: при неопределённом исходе сначала receipt, а не новый ID или новая запись.

## 7. Конфликт сохранённой версии

Открытая форма хранит baseRevision; сохранение не перезаписывает молча более новую запись. При несовпадении либо удалённой целевой записи факты остаются прежними, raw-draft сохраняется; показывается, что данные изменились. Пользователь может вернуться к своей форме или явно загрузить актуальную версию с предупреждением о замене draft. Автоматического merge, обновления снимков или превращения правки в новую запись нет.

Правило действует и офлайн: два окна/редактора, повторный вход, отложенная запись и уже завершённая операция возможны без облачной синхронизации. Уникальные дата веса/сна/начала цели и имя приёма проверяются в той же транзакции. Занятое назначение обрабатывается предусмотренным UX правки/подтверждения, а не SQL replace с потерей связей. Revision увеличивается с проверкой переполнения; время устройства не используется как единственный порядок конфликтов.

Для нового назначения факт использует активный приём. Восстановленный исторический редактор сохраняет исходный ID, включая архив, и не переназначает его на первый активный. Если изменившийся список требует нового назначения, оно выбирается явно.

## 8. Независимые предпочтения DataStore

Тема, шрифт, акцент/обложка, главная, игровые переключатели и малый контекст фильтров находятся в **одном DataStore-файле**, вместе с соответствующим preference_draft, revision и receipt/applyToken. Это другой backend, не часть Room-транзакции. Persistent draft этих визуальных настроек в Room не дублируется; мост Room↔DataStore и pending_preference_writes не вводятся.

Для формы с явным сохранением:

1. Checkpoint записывает только preference_draft; committed-предпочтения остаются прежними, UI может показывать живой предпросмотр.
2. Одна updateData сначала возвращает совпадающий готовый receipt/token без требования живого draft; для ещё не выполненной команды проверяет baseRevision редактируемой группы, атомарно записывает **весь** подтверждённый набор, новую revision и receipt/applyToken, закрывает этот draft. Только после успешного завершения обновления показан успех.
3. При прерывании до commit остаются прежние предпочтения и предыдущий checkpoint. После commit, но до отображения результата, receipt/token подтверждает успех; повтор не применяет действие снова.
4. Более старый draft/retry после другого сохранения отклоняется по baseRevision, если его результат уже нельзя однозначно вернуть из receipt; не перетирает новый выбор и не объявляется новой операцией. Тот же ID с иным fingerprint — конфликт. Receipt хранится как минимум пока достижим связанный draft/retry; удаление служебного состояния не должно разрешать повторное применение старой команды.

Revision относится к редактируемой группе: appearance (акцент/обложка), home layout, независимые прямые theme/font/game flags и контекст просмотра имеют отдельные revision. В файл записывается целиком новая группа с сохранением остальных, а не старый снимок всех предпочтений. Скролл/фильтр просмотра не создаёт ложный конфликт открытого оформления; внешний reset той же группы создаёт конфликт/явную переинициализацию. Для целей domain draft также несёт goalTimelineRevision предпросмотра: соседняя вставка/удаление цели требует нового предпросмотра и подтверждения.

Discard также меняет только данные того же DataStore и откатывает UI к committed-набору; поздний checkpoint не воскрешает закрытый draft. Прямой переключатель/подтверждённый reset использует одну атомарную запись с revision/token и согласованным закрытием заменяемого draft. Повторный reset не возвращает прежний пользовательский набор через старую отмену.

Связанные с каталогом быстрые порции и спецификации напоминаний/их drafts остаются в Room. Применение системного расписания требует повторяемого протокола отдельно от состояния разрешения и доставки; конкретный планировщик остаётся TECH-007. Документ не обещает атомарно сохранить БД и доставить Android-уведомление. Ошибка DataStore не сбрасывает дневник, ошибка Room не заменяет визуальный набор дефолтами.

## 9. Фото и согласованность файлов

`media_assets` хранит идентичность собственного локального ресурса; `draft_media` удерживает существующие и подготовленные файлы до решения пользователя. Два одинаковых входных файла могут относиться к разным photoID/подписям. Удаление одного фото не должно подменять второе при восстановлении.

Принцип двух фаз:

- **Подготовка:** скопировать/проверить ресурс выбранной стратегией, получить стабильный internal object key и связать его с draft. Пока подготовка не завершена, сохранение недоступно; ошибка/отмена не создаёт ссылку факта. URI оригинала сам по себе не считается собственной надёжной копией.
- **Подтверждение:** только готовые ресурсы связываются с сохранёнными photoID/днём в атомарной Room-операции. Для добавления/замены/удаления публикуется целый согласованный результат дня. Если реализация требует дополнительного файлового finalize, его журнал/готовность/повтор и момент допустимого UI-успеха должны быть определены до этапа фото в TECH-005; одного SQL commit недостаточно.

Сбой до записи draft-ссылки оставляет потенциальный staging-файл; сбой после неё оставляет ресурс активного draft; сбой после подтверждения БД — ресурс факта. Уборка проверяет ссылки всех трёх владельцев: факт, живой draft и незавершённая операция. Нельзя удалять файл только по возрасту, названию временного каталога или отсутствию в фотоленте. Подтверждённое удаление/замена допускает уборку старого файла лишь после сохранения нового состояния и проверки остальных ссылок.

При старте recovery согласует состояния без автоматического добавления несохранённого фото. Недоступный/повреждённый ресурс показывается ошибкой, не молча исчезает из истории. Точные каталоги, fsync/rename, EXIF/миниатюры, квоты и очистка остаются TECH-005; договор о двух фазах не является готовым файловым алгоритмом.

## 10. Восстановление экрана и ожидаемые проверки

После старта сначала открыть совместимое хранилище/завершить нужные миграции, сверить receipts и состояния ресурсов в соответствующем backend и только затем восстановить маршрут. Закрытый/discarded draft не показывается вновь; успешный receipt открывает результат. Для открытого draft восстанавливаются последние подтверждённые поля, шаг и выбранная дата с повторной валидацией. Если ссылка маршрута устарела, показать понятный возврат к существующему разделу, не создавать взамен объект.

ViewModel, SavedStateHandle/rememberSaveable и сериализуемые ключи Navigation 3 помогают восстановлению UI, но не заменяют постоянный draft для restart/reboot. В Bundle/back stack достаточно ID/ключей и небольшого контекста; снимки больших составов и фото читаются из локального хранилища. Отсутствие восстановленного Bundle не означает, что черновик можно удалить.

Ожидаемые проверки, **ещё не запускались**:

| Ситуация | Ожидаемый результат |
|---|---|
| ON-002/003: частичная/невалидная цель, завершённый checkpoint, restart и «позже» | Шаг/raw-поля сохранены, активной цели нет, onboarding не повторяется после завершения |
| AN-002: поворот/process death/reboot до/после checkpoint | Последний подтверждённый checkpoint возвращается; ввод до checkpoint не объявляется гарантированно сохранённым |
| Несколько полей/строк, завершение старой записи после новой | Новая revision не перезаписана; поздний debounce не воскрешает закрытый draft |
| Грязный Back, отмена диалога/подтверждённый discard | Сначала форма прежняя, затем draft закрыт без изменения факта; фильтры происхождения сохранены |
| AN-003: kill до/после Room commit, двойной тап/retry | Прежнее либо полное новое состояние; receipt даёт один результат и те же ID |
| Другая revision/удалённый target/архив назначения | Понятный конфликт, нет молчаливого overwrite/merge/нового факта |
| DataStore commit, kill до отображения; ошибка до commit | Набор+receipt+закрытие draft применены целиком либо не применены; новый выбор не перетирается старым retry |
| CV-007/010: перенос и фото, disk full/отмена picker/сбой фаз | Нет половины состава/дня, потери прежних ресурсов или удаления файлов активного draft |
| Обновление приложения с открытым старым draft и receipt | Формат переносится либо явно недоступен без удаления; подтверждённая операция не повторяется |
| Поиск/фотолента/отчёт при открытом draft | Только подтверждённые данные; raw invalid filters не запускают подменённый запрос |

Первичные источники, прочитанные при подготовке:

- [Android: сохранение UI-state](https://developer.android.com/topic/libraries/architecture/saving-states) — память, saved state и постоянное хранение имеют разные границы жизненного цикла.
- [Compose state saving](https://developer.android.com/develop/ui/compose/state-saving) — Bundle/SavedStateHandle для малого состояния и ID, а не больших объектов.
- [Navigation 3 save state](https://developer.android.com/guide/navigation/navigation-3/save-state) — приложение владеет back stack, ключам нужны NavKey/сериализация; постоянный draft проектирует Diet.
- [DataStore](https://developer.android.com/topic/libraries/architecture/datastore) — атомарное хранение небольшого набора не распространяется на Room/файлы.
- [SQLite atomic commit](https://www.sqlite.org/atomiccommit.html) — атомарность относится к транзакции БД; медиа и внешние эффекты требуют собственного протокола.

Checkpoint, подтверждение, конфликты и идемпотентность выбраны документально. Схема/реализация/параметры debounce и проверка recovery после прерываний остаются будущей частью TECH-004/005/009.
