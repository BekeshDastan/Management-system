# Diet — ввод и обработка личных фото

Дата: 15 ноября 2026 года. **Статус: инженерный контракт TECH-005; Android-код, декодеры и испытания Diet ещё не созданы.** Числа ниже выбраны для будущей реализации, не измерены на телефонах. Продуктовые ограничения остаются из [правил данных](data-rules.md): до четырёх фото на дату, входной файл не больше 5 × 1024 × 1024 байт, JPEG/PNG/WebP.

Этот документ определяет преобразование изображения и управляемую память. Файлы/Ready, привязка batch, recovery, удаление и приватность — media-storage.md (публикуется отдельной частью); доменные операции — [модель](storage-model.md) и [черновики](drafts.md). Не вводятся камера, OCR/ML, распознавание еды, HTTP-загрузка, обязательный GMS или чтение всей галереи.

## 1. Выбор и граница batch

1. Перед открытием посчитать freeSlots = 4 − число фото в текущем редактируемом наборе, включая ранее подготовленные. При нуле picker не открывать; UI объясняет предел.
2. При одном свободном месте использовать PickVisualMedia; при двух–четырёх — PickMultipleVisualMedia с верхним пределом 4 и request.maxItems = freeSlots либо эквивалентным пределом контракта. Multiple требует максимум больше 1.
3. Запрашивать ImageOnly. Контракт предпочитает framework picker, затем системный fallback, затем ACTION_OPEN_DOCUMENT. Отсутствие GMS не доказывает отсутствие framework/OEM picker; приложение проверяет возможности, а не марку телефона.
4. ACTION_OPEN_DOCUMENT не обеспечивает заданный максимум. Callback с числом URI больше freeSlots отклоняется **целиком**, без молчаливого выбора первых файлов. Ноль URI — отмена, а не ошибка или удаление прежних фото.
5. Одновременно активен один импортируемый batch, максимум четыре входа. Дата, ID редактора и revision заморожены; поздний callback после ухода/отмены не меняет другой день. При окончательном сохранении повторно проверяются revision и предел четырёх фото.

Это план применения выбранного Activity API, не готовый launcher. Основания: [Photo Picker](https://developer.android.com/training/data-storage/shared/photo-picker), [контракт multiple](https://developer.android.com/reference/androidx/activity/result/contract/ActivityResultContracts.PickMultipleVisualMedia), [исходник AndroidX с проверкой maxItems](https://raw.githubusercontent.com/androidx/androidx/androidx-main/activity/activity/src/main/java/androidx/activity/result/contract/ActivityResultContracts.kt).

## 2. Получение входных байтов

URI — разрешённый источник импорта, не постоянный ресурс Photo. Picker/SAF могут показать локальное или облачное содержимое. Доступность удалённого файла, сеть провайдера, сроки загрузки и одинаковое поведение разных providers не обещаются. Работа Diet с уже сохранёнными фото остаётся офлайн; приложение не получает INTERNET ради импорта. Сеть выбранного внешнего provider этим не запрещается.

- Читать через ContentResolver в собственный staging потоково. Не загружать целиком в ByteArray/Bundle и не искать «реальный путь» в общей галерее.
- Имя, MIME и SIZE провайдера — подсказки. SIZE может отсутствовать; лимит проверяется фактическим счётчиком байтов с остановкой при 5 MiB + 1. Пустой поток, отказ доступа, ошибка чтения, отмена и disk full не создают Ready/Photo.
- Импорт выполняется только в foreground: временный grant используется до завершения копирования, persistable grant не запрашивается, URI не сохраняется для продолжения. При process death весь batch до Ready отменяется и требует повторного выбора; уже Ready-ресурсы с durable refs сохраняются. Исходный URI не нужен для показа готового master.
- CancellationSignal используется там, где поддержан resolver API; также закрываются принадлежащие задаче потоки/дескрипторы. Отмена провайдера не объявляется универсальной гарантией мгновенного прерывания.

Основания: [SAF и неизвестный размер](https://developer.android.com/training/data-storage/shared/documents-files), [ContentResolver](https://developer.android.com/reference/android/content/ContentResolver), [срок доступа picker](https://developer.android.com/training/data-storage/shared/photo-picker#persist-media-file-access).

## 3. Валидация до выделения пикселей

После завершённой копии работать с теми же собственными байтами, а не повторно получать меняющийся источник. Проверить сигнатуру контейнера и настоящий MIME декодера: только JPEG, PNG, WebP. Расширение и заявленный provider MIME не подменяют эту проверку; сигнатура сама по себе не доказывает исправность изображения.

| Проверка исходника | Выбранная граница / результат |
|---|---|
| Размер входа | 1…5 242 880 байт включительно |
| Каждая исходная сторона | 1…32 768 пикселей включительно |
| Площадь | width × height ≤ 64 000 000, проверяемое целое умножение |
| Тип и целостность | Разрешённый decoder MIME, валидные bounds, успешно декодированный выбранный кадр; partial/error не принимается |
| Анимация WebP | Нормализовать первый кадр в неподвижное фото; до сохранения показать превью и пояснение «Сохраняется как фото» |

Пределы сторон/площади — инженерная защита, не прежний макетный предел 16 000 px. Файл до 5 MiB всё равно может превышать их; отказ объясняется размером изображения и сохраняет прежний день/draft. Эти границы не обещают защиты от любого повреждённого контейнера или расхода системного codec.

Предпочтительный API для всей minSdk 29 — ImageDecoder, доступный с API 28. Header listener проверяет ImageInfo, MIME/animation/bounds, задаёт sample/target до pixel decode. Partial image listener не разрешает частичный результат. BitmapFactory с inJustDecodeBounds — возможный проверяемый запасной путь, не параллельное полное декодирование. [ImageInfo](https://developer.android.com/reference/android/graphics/ImageDecoder.ImageInfo), [bounds/sample](https://developer.android.com/topic/performance/graphics/load-bitmap).

## 4. Нормализованный master

- ImageDecoder использует ALLOCATOR_SOFTWARE, целевой размер по разделу 6 и целевое sRGB. Hardware bitmap не используется в этой обработке. Decode выполняется вне UI-потока.
- ImageDecoder учитывает EXIF origin, включая поворот/отражение; повторно применять ручной EXIF-поворот нельзя. Размер назначения относится к уже ориентированному изображению, стороны второй раз не переставляются.
- Проверить все восемь EXIF orientation. Если понадобится BitmapFactory-ветвь, orientation обрабатывается явно: по ExifInterface сначала горизонтальное отражение, затем rotationDegrees. Отсутствующая ориентация не придумывает поворот.
- Результат рисуется целиком, без crop, на **новый непрозрачный ARGB_8888/sRGB bitmap с белым фоном**. Прозрачность PNG/WebP сводится на этот фиксированный фон, независимо от темы приложения.
- Новый bitmap кодируется в JPEG с quality 85. Исходные EXIF/GPS, подписи, embedded thumbnail и gainmap в выход не копируются; дата/подпись Diet остаются отдельными данными. Новый canvas не должен наследовать gainmap исходного bitmap.
- Длинная сторона master ≤ 2048, увеличения исходника нет; фактический размер зависит от памяти. Это оптимизированная локальная копия, **не побайтовый архив оригинала**. Превью объясняет статичность/оптимизацию и показывает фактический результат.
- Завершить encoder, flush/fsync открытого выходного дескриптора и close, проверить успешное кодирование и размер ≤ 5 MiB, заново проверить JPEG/размеры/ориентацию/отсутствие исходных EXIF/GPS/gainmap. Проверка контейнера/метаданных выполняется без нового полного bitmap. Если нужна повторная pixel-проверка, прежние worker-bitmaps сначала освобождаются либо все дополнительные allocations включаются в бюджет. Только проверенный результат передаётся lifecycle как подготовленный.
- Если JPEG превысил 5 MiB, освободить worker-bitmaps и повторить со следующим меньшим профилем раздела 6, сохраняя quality 85. Максимум шесть различных профилей; не снижать качество скрыто. После исчерпания — явная ошибка без Ready.

Исходный staging хранится только для текущего файла до его проверенного и надёжно записанного master, затем удаляется перед обработкой следующего файла. Весь batch до общей готовности остаётся PREPARING без новых draft refs; исходники не хранятся как дополнительные оригиналы. Не добавляется функция экспорта оригинала.

Основания: [ImageDecoder software/target/sRGB](https://developer.android.com/reference/android/graphics/ImageDecoder), [применение origin в AOSP](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/master/libs/hwui/hwui/ImageDecoder.cpp), [ExifInterface](https://developer.android.com/reference/androidx/exifinterface/media/ExifInterface#getRotationDegrees()), [Bitmap: sRGB и JPEG](https://developer.android.com/reference/android/graphics/Bitmap). Цвет/UltraHDR/нестандартные профили проверяются на фикстурах; без испытаний точное совпадение с отображением исходной галереи не обещается.

## 5. Бюджет управляемой памяти

MiB = 1 048 576 байт, KiB = 1024 байта. H — числовое значение memoryClass, трактуемое в MiB для этого контракта; lowRam берётся из isLowRamDevice, не из предположения по модели. Большой heap не запрашивается ради обхода бюджета. [ActivityManager](https://developer.android.com/reference/android/app/ActivityManager#getMemoryClass()).

| Обозначение | Плановая формула |
|---|---|
| B: общий управляемый бюджет | min(80, floor(H / 4)) MiB; на lowRam дополнительно не больше 24 MiB |
| Минимум | При B < 8 MiB — понятная ошибка ресурсов без потери сохранённых данных; импорт не начинается |
| C: memory-LRU | min(8 MiB, floor(B / 8)) |
| R: оценочный резерв codec/native | min(16 MiB, floor(B / 4)) |
| IO | 256 KiB резерва потоковой обработки |
| L: фактические живые bitmaps | Сумма уникальных allocationByteCount у уже живых bitmap, кроме новых worker-буферов, учтённых отдельно ниже |

B — инженерный предел управляемых изображений/резервов, **не hard cap всего heap, native или GPU**. ARGB_8888 — 4 байта/пиксель; software ImageDecoder может вернуть F16 с 8 байтами/пиксель. sRGB/allocator не являются обещанием ровно четырёх байт. R — оценка дополнительных буферов, не доказательство верхней границы любого decoder. [Bitmap.Config](https://developer.android.com/reference/android/graphics/Bitmap.Config), [реальная allocation](https://developer.android.com/reference/android/graphics/Bitmap#getAllocationByteCount()).

## 6. Выбор размера до decode

1. Сначала вытеснить неиспользуемые элементы memory-LRU, затем пересчитать L по реестру уникальных allocations. Bitmap, удерживаемый UI, остаётся в L после удаления cache-entry; eviction не означает освобождение его памяти.
2. Проверить по убыванию S = {2048, 1536, 1024, 768, 512, 256}. targetLong = min(S, sourceLong); сохранить соотношение сторон целочисленно вниз, короткая сторона минимум 1. Ни одна сторона не увеличивается. Одинаковые target-размеры повторно не проверять.
3. Выбрать наибольший профиль, для которого **12 × targetW × targetH + R + IO + L ≤ B**. Это 8 байт для sampled decode output и 4 для нового canvas; не 8 байт для полного исходного разрешения. Арифметика checked до выделения.
4. Допустима более консервативная оценка 12 × S² вместо площади прямоугольника. Если не помещается даже минимальный профиль, показать ошибку ресурсов; прежнее фото/редактор сохраняются.
5. До decode задать точный targetW/targetH через ImageDecoder.setTargetSize; последующий setter sample не должен переопределить рассчитанные размеры. Проверить фактический config/allocation и размеры, учитывать временные буферы; при непредвиденном превышении не создавать следующий большой буфер/Ready. Не полагаться на API setAllocationLimit: он появился лишь в version 37.2, а выбрана compileSdk 37 minor 0.
6. При переполнении encoded JPEG повторять меньший профиль только после завершения прежней попытки и освобождения её worker-ресурсов. Проверить budget заново: L мог измениться. Ошибка decode/OOM не становится автоматическим циклом повторов.

Иллюстрации для квадратного входа не меньше S, **L=0**, обычного non-lowRam; MiB-значения рассчитаны по формулам, не измерены на устройстве:

| H | B | C | R | Наибольший S | 12 × S² + R + IO |
|---|---|---|---|---|---|
| 64 | 16 | 2 | 4 | 768 | 11 MiB |
| 128 | 32 | 4 | 8 | 1024 | 20,25 MiB |
| 256 | 64 | 8 | 16 | 1536 | 43,25 MiB |
| 512 | 80 | 8 | 16 | 2048 | 64,25 MiB |

При H=64 профиль 1024 требует 16,25 MiB и не проходит. На lowRam с H=128 B=24 MiB, C=3 MiB, R=6 MiB; это отдельная ветвь. Живые UI-изображения могут уменьшить выбранный размер. Формулы не доказывают отсутствие OOM; реальные peak/скорость/codec-особенности входят в будущие TECH-009 испытания.

## 7. Очередь, отмена и ошибки batch

Один **глобальный тяжёлый job** одновременно: import/decode/view decode/canonical-normalise/подготовка миниатюры. Все четыре файла batch обрабатываются последовательно; четыре full-resolution bitmap одновременно не удерживаются. Работа и дисковый IO идут вне UI-потока; отменённая задача не перекрывается новым тяжёлым decode, пока её native-вызов не вернулся.

Отмена проверяется между фазами, прекращает принадлежащий задаче IO и запрещает публикацию позднего результата. Она не объявляет native память уже свободной. Не использовать requestCancelDecode как защиту: на min29 он не останавливает decode. OOM/ошибка ресурса — отказ подготовки без нового фото; UI получает ошибку, ссылки/worker-ресурсы освобождаются безопасно, повтор требует нового действия пользователя. [BitmapFactory.Options](https://developer.android.com/reference/android/graphics/BitmapFactory.Options#requestCancelDecode()).

Batch all-or-none: при ошибке любого файла никакое новое фото этого выбора не добавляется в durable draft. Прежние текстовые поля/день/ранее существовавшие photo refs сохраняются. Только после готовности и надёжной записи **всех** новых ресурсов lifecycle привязывает их одним checkpoint-транзакционным действием; это ещё не явное сохранение дня. SQL-транзакция не объявляется атомарной с файловой записью: подготовка файлов предшествует привязке. Pending/orphan файлы обрабатывает lifecycle, не отображаемая фотолента.

## 8. Миниатюры, просмотр и пути

Миниатюра: длинная сторона ≤ 320 без upscale, JPEG quality 75, encoded ≤ 256 KiB. Это необязательный восстанавливаемый результат из master. Ошибка/отсутствие миниатюры не повреждает master и не удаляет сохранённое фото; можно повторить генерацию/показать placeholder. Дисковый LRU производных ресурсов — максимум 128 MiB; memory-LRU ограничен C, а все живые UI-bitmaps также учитываются в L. [Кэш изображений](https://developer.android.com/topic/performance/graphics/cache-bitmap).

Крупный просмотр декодирует master под viewport с соблюдением B и исходных размеров master. Не добавляются pan/zoom/tiling или чтение полного оригинала как новая функция. ImageDecoder.setCrop не заменяет memory-bounded BitmapRegionDecoder; region-путь не нужен выбранному ограниченному master/viewer. [ImageDecoder crop](https://developer.android.com/reference/android/graphics/ImageDecoder#setCrop(android.graphics.Rect)), [region API](https://developer.android.com/reference/android/graphics/BitmapRegionDecoder).

Пути логические, не созданные каталоги: `<dataRootNoBackup>/media/objects/<assetId>.jpg`, staging в `<dataRootNoBackup>/staging/<batchUUID>/`; миниатюры — `cacheDir/diet-media/`. В БД — внутренний ключ/метаданные, не URI галереи, абсолютный пользовательский путь или bitmap. LRU не удаляет master/staged ресурс живого draft/pending-операции. Проверка исключения cloud/D2D остаётся отдельным TECH-006.

| CV-009/010, ST-011 | Все EXIF 1…8 с несимметричными метками; static/animated WebP, прозрачные PNG/WebP; sRGB/широкий gamut/UltraHDR; сохранённый результат без GPS/EXIF/gainmap |
